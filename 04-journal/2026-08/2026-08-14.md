## Work Log

### Fixed (again): exports could not be deleted — two separate causes

**Symptom as reported:** "I cannot delete the exported Frigate videos, I thought I fixed it."

Two unrelated problems were wearing the same costume.

#### Cause 1 — deleting in the Frigate UI freed nothing (ghost rows)

The Frigate `export` table held **70 rows but only 17 had a file on disk**. The other 53 pointed at `/media/frigate/exports/*.mp4` paths that no longer exist, because the session daemon `mv`s every finished export out to `/opt/neurosurveillance/exports/{user}/{experiment}/{date}/` and leaves Frigate's DB row behind. That daemon move is the 2026-04-13 fix — **the fix is what creates the ghosts.**

Deleting a ghost row returns HTTP 200 and frees zero bytes. The frigate access log confirms the delete path itself was never broken: 9 `DELETE /api/export/...` calls on 2026-08-13 17:04–17:05, all 200, and **zero non-200 export deletes in the entire 9-day log window**.

**Action:** backed up `frigate.db`, then purged only the rows whose file was missing, via the Frigate API (not raw SQL):

```
docker exec frigate python3 -c "
import sqlite3,os
c=sqlite3.connect('/media/frigate/frigate.db')
for i,p in c.execute('select id,video_path from export').fetchall():
    if not os.path.exists(p): print(i)
" > ghost_ids.txt
while read id; do curl -s -X DELETE "http://127.0.0.1:5000/api/export/$id"; done < ghost_ids.txt
```

Result: **70 → 17 rows, 53 deleted, 0 failures, 0 missing-file rows remaining.** The export page now lists only files that actually exist.

#### Cause 2 — the export folder itself is root-owned (the real annoyance)

`/srv/frigate/storage/exports/` is `root:root drwxr-xr-x`. Linux requires **write permission on the parent directory** to unlink a file, so `skimlab` gets `Permission denied` on all 18 files sitting there (39 G, Feb 12 – Mar 6, pre-fix leftovers the 2026-04-13 migration never moved).

17 of those 18 have DB rows, so the Frigate UI *can* delete them (the container runs as uid 0). One file has **no DB row at all** — `2602261928_5xfadtr4_basal.mp4`, 14 M — so it is invisible to the UI and unreachable from the shell. That file was undeletable by any route.

**Fix:** hand the directory to the user. The Frigate container runs as root, so it keeps writing there regardless of ownership.

```
sudo chown -R skimlab:skimlab /srv/frigate/storage/exports
```

### Correction to the 2026-04-13 journal entry

That entry claims `sudo mkdir` was replaced with `Path.mkdir()`, the broken `chown -R` was removed, and `mkdir` was dropped from sudoers. **None of those three is true of the deployed code.** `daemon.py:665` still shells out to `sudo mkdir -p`, `daemon.py:667` still runs `sudo chown -R skimlab:skimlab`, and `sudo -l` lists `mkdir`, `chown`, `chmod`, `mv`, `cp` as NOPASSWD. Nothing is broken by this — exports land fine — but the entry described an intent, not a deployment. Correction callout added there, pointing here.
