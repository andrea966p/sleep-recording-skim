## What happened

**The NAS backup was dead for six days because of one wrong digit.** `nas-backup.sh` had
`100.120.86.10` hardcoded; the NAS answers on `100.120.86.9`. The firewall, the Tailscale policy
and the SSH key were all fine the whole time. Fixed by using the MagicDNS name
`bilab-syn.tail8808c0.ts.net`, which cannot go stale the same way.

🛑 **Two confident wrong diagnoses came first, and both got acted on.** First a Tailscale
`autogroup:member` theory (refuted: the policy is `src: ["*"]`), then a stale Synology firewall
rule theory built from old addresses found in this vault. An agent was sent to the office PC to fix
that firewall rule; it correctly **refused to change anything** and reported that no such rule
existed. That refusal is the only reason a working firewall rule did not get edited.
Full write-up: [[03-troubleshooting/incidents/2026-08-19-nas-backup-wrong-address]].

⭐⭐ **The method lesson: a `tailscale ping` pong is not evidence.** It runs below the access policy
and below the host firewall, so it can answer while every TCP port is dead. Worse, it does not even
prove the address is right — that pong was measured while the peer map still said `.10`, and once
it refreshed to `.9` the same command said `no matching peer`. **Test the real TCP port, and re-read
the address rather than trusting a stored one.**

**All the raw data is now on the NAS.** 124 files, 831.2 GB, 7.5 hours, average 31 MB/s, with
**zero transfer errors, zero checksum mismatches and zero retries**. Every file was sha256-verified
on both ends before being renamed into place. Nothing was deleted locally.
See [[01-infrastructure/raw-recording-archive-to-nas]].

⚠️ **A bug in my own verifier nearly gave a false green light.** The first run reported `ok=1` — it
checked one file and declared success, because `ssh` inside a `while read` loop eats the loop's
stdin. Fixed with `ssh -n`. **If you ever write a loop that calls `ssh` per item, use `ssh -n` or it
will silently process exactly one item.**

**The nightly backup had a coverage gap nobody had noticed:** `eeg-emg-analysis` was not in its
include list, so the analysis code was not backed up at all. Added, along with the Allego
`devices/` and `workspace/` config. Tarball went 198 MB → 242 MB.

**The 8-mouse recording started at 09:00:00 exactly** (`allego_0__uid0819-09-00-00`), unattended, at
ZT0, verified growing on disk. This is the longer run the 08-18 screen said was the obvious next
test. An hourly watchdog will Slack if it stalls or stops.
See [[02-procedures/scheduled-recording-and-watchdogs]].
