## Everything is archived: 130 files, 1.01 TB

The two new runs (31.2 GB + 149.7 GB = 182.3 GB) were copied to the NAS and verified. Independent
cross-check afterwards, not trusting the script's own report:

| Check | Result |
|---|---|
| File counts | local 130 = NAS 130 |
| Leftover `.part` files | 0 |
| Sum of file bytes | **1,013,471,371,569 on both sides, exact** |
| Per-file size diff across all 130 | **no differences** |
| Fresh sha256 of the 149.7 GB run vs the manifest | **match** |

> [!note] A 9,820-byte discrepancy that was NOT a problem
> `du -sb` initially showed the NAS as 9,820 bytes larger. That is the **directory inode itself**,
> which differs between ext4 and the NAS filesystem. Summing file sizes only, both sides are
> byte-identical. Worth remembering before anyone raises an alarm over it: compare files, not `du`.

Transfer ran at 60-70 MB/s. The slow part is not the network — it is the NAS computing sha256 over
149.7 GB, which took about an hour of the total.

### Two fixes to the archive while it was idle

- **`ARCHIVE_IGNORE_WINDOW=1`** lets a deliberate manual run bypass the 08:30-20:00 window. That
  window is only a crude proxy for "do not compete with a recording"; the recording check is the
  real protection and the override does **not** touch it.
- **The manifest lookup now happens before the rig query.** `recording_active()` spawns a python
  client and costs ~3.3 s, so asking it about already-archived files wasted about seven minutes on a
  resumed run. A full re-scan of 130 files went from ~7 minutes to **4.3 seconds**.
