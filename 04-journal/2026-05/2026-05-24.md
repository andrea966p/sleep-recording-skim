## Phase 3.1 — Frigate restart grace (LWT path)

`FrigateController` gained three concerns:

| Surface | Behavior |
|---|---|
| `_on_connect` | Now subscribes to `frigate/available` alongside `frigate/+/recordings/state` and resets `_initial_available_seen` so the very first retained payload after every (re)subscribe is treated as a baseline read rather than a Frigate restart. |
| `_handle_availability_message(payload)` | First non-initial `online` calls into the daemon's `_handle_frigate_availability_change` callback. `offline` is logged but not actionable. |
| `register_frigate_availability_callback(callback)` | Public hook; the daemon registers `_handle_frigate_availability_change` after the same conditions as the existing external-recording callback (i.e. only when `manual_sessions_enabled`). |

Council Stage 2.3 fold-in: a new `_last_known_state_lock` guards every read/write of `_last_known_state`. The lock is held briefly (one `dict.get` + assignment); two near-simultaneous MQTT messages can no longer observe the same `prev` value.

Daemon side:

- New module constant `FRIGATE_RESTART_GRACE_SECONDS = 10` (mirrors the startup grace).
- `_handle_frigate_availability_change(current, previous)`: fires from the MQTT callback thread; spins up `_frigate_restart_grace` in a background thread guarded by `_restart_grace_active` + `_restart_grace_lock` so availability flaps cannot stack parallel grace windows.
- `_frigate_restart_grace(previous)`:
  1. `register_external_recording_callback(None)` — suppress
  2. `cancel_pending_state_actions()` — kill any in-flight defers
  3. `_shutdown_event.wait(FRIGATE_RESTART_GRACE_SECONDS)` — interruptible sleep
  4. `clear_expected_states()` + `clear_last_known_state()` — fresh baseline
  5. `register_external_recording_callback(self._handle_external_recording_change)` — re-arm

## Phase 3.1b — Ordering bug fix (caught during the 3.2 regression)

The initial 3.1 wiring still produced 4 phantom `ManualSession`s per restart. Cause: Frigate republishes its retained topics in the order they were last published — `recordings/state` *before* `frigate/available`. The callback was therefore running *before* the availability handler could clear it.

Three observations confirmed the cause:

1. `docker exec mosquitto mosquitto_sub -t 'frigate/available' -v` during a restart showed two `online` payloads only (no `offline` LWT in the test window) — keepalive longer than the restart duration.
2. Manually publishing `mosquitto_pub -t 'frigate/available' -m offline` *then* `-m online` produced the **correct** sequence in the daemon log (grace ran cleanly). That ruled out the daemon-side logic; the problem was message ordering.
3. The journalctl trace of the failing restart showed `External recording state change: pi_cam_X -> ON (was OFF)` → `Manual recording started session=…` happening **before** `Frigate availability: online`.

**Fix**: every external-state callback is now wrapped in a `threading.Timer`. New constant `STATE_DEFER_SECONDS = 1.5`. When a `recordings/state` transition is detected, `_schedule_state_callback` arms a timer; the callback fires from a worker thread only after the delay elapses. An availability `online` arriving during the delay calls `cancel_pending_state_actions()` from inside the same MQTT callback thread (paho processes messages sequentially on its loop thread, so the cancel runs in-order with respect to subsequent state messages).

Belt-and-suspenders cancel also lives in `_frigate_restart_grace` after the callback is cleared, so a deferred timer that somehow survives still no-ops.

The defer also gives benign side effects:

- A rapid `ON → OFF → ON` from a Frigate UI double-click within 1.5 s collapses to the most recent payload — `_schedule_state_callback` cancels any previously-pending timer for the same camera before arming a fresh one.
- The `start_recording` path that creates a session is now 1.5 s slower than before. Acceptable — Frigate's own export latency dominates.

Regression validated:

```
journalctl --since "5 minutes ago" -u neurosurveillance-session \
  | grep -c "Manual recording started"
# 0
```

across three consecutive `docker restart frigate` cycles at 11:19:41, 11:21:58, and 11:22:38.

## Phase 3.3 — `backend/reconciler.py`

Single module, ~535 lines, ~340 of which are the class. Defined contracts:

| Surface | Responsibility |
|---|---|
| `Reconciler(journal_db_path, frigate_db_path, tz, mqtt_publish, scheduled_hour, scheduled_minute, window_hours)` | Constructor. All paths resolved at instantiation; the read-side opens short-lived read-only sqlite connections per call. |
| `start()` / `stop()` | Background-thread lifecycle. Daemon calls both in `start()` / `stop()` next to `storage_monitor` and `watchdog`. |
| `run_once(window_hours=None) -> dict` | Synchronous reconciliation pass. Returns the findings dict; also stores it under `get_last_findings()` and publishes the compact summary to MQTT (if `mqtt_publish` is wired). Thread-safe (single `_lock` guards `_last_findings`). |
| `get_last_findings() -> Optional[dict]` | Read-side. Returns a shallow copy of the last findings or `None`. |

**Finding categories**:

| Category | Rule | Notes |
|---|---|---|
| ORPHAN | Continuous Frigate segment runs not covered by any WAL `START` interval, where the uncovered span ≥ `MIN_ORPHAN_DURATION_S = 21600` (6h). | Frigate's `record.enabled: true` records 24/7 regardless of sessions, so per-minute gaps would flood the report. The 6h floor surfaces only outsized anomalies. Slack alerts intentionally suppress this category. |
| PARTIAL | Session has `START` + closing event (`EXPORT_COMPLETE` or `ABORT`) within the window; Frigate's segment-second coverage over `[start, end]` is `< PARTIAL_RATIO = 0.5`. | Skipped if `START` is older than `FRIGATE_RETENTION_DAYS = 7` (no segments exist to compare against). |
| STUCK | `EXPORT_BEGIN` row older than `STUCK_EXPORT_HOURS = 24` with no matching `EXPORT_COMPLETE`. | Skips rows with `payload.backfilled == true` (no `EXPORT_BEGIN` was ever written for backfilled history). |
| DEGRADED | Session has `START` + `EXPORT_COMPLETE` + at least one `STALL` event between them. | Bonus category beyond the original sprint spec; surfaced by 2026-05-23's STALL → session_id wiring. QC flag, not data loss. |

**Schedule loop**:

```python
def _loop(self):
    while not self._stop.is_set():
        now = datetime.now(self.tz)
        sleep_for = self._seconds_until_next_run(now)
        logger.info("Reconciler next run in %.1f minutes (at %02d:%02d %s)", …)
        if self._stop.wait(sleep_for):
            return
        try:
            self.run_once()
        except Exception as e:
            logger.exception("Reconciler tick failed: %s", e)
```

`_seconds_until_next_run` advances `target` by one day whenever it has already passed today, so first start after 00:01 sleeps ~24 h, not 0.

**API**:

```
GET  /api/reconciler/last                 -> last findings dict (404 if never run)
POST /api/reconciler/run?window_hours=N  -> synchronous ad-hoc run + findings
```

Both endpoints check `_reconciler is None` and return `503` if the daemon hasn't initialized.

**CLI**:

```bash
/opt/neurosurveillance/venv/bin/python reconciler.py \
    --since 24h --dry-run --json
```

`--dry-run` is implicit when the script is invoked standalone (no `mqtt_publish` callable is passed). The CLI shares the same `Reconciler` class — different mode, same code path.

**Why MIN_ORPHAN_DURATION_S = 6h**:

The first dry-run (no orphan threshold) reported 25 ORPHANs across 7 days. Tracing one: WAL session `8f2b89a1` (Diane, May 20 16:37:15 KST → May 22 18:35:06 KST) covered her actual recording window in the WAL correctly. The reported ORPHANs were *other* continuous Frigate runs outside Diane's session — Frigate's `record.enabled: true` mode keeps writing segments whenever it's running, regardless of whether a daemon-tracked session exists. The 25 reported ORPHANs were all in this category, not bugs. With 6h floor, post-deploy 7d run reports 0. If we ever toggle to "Frigate records only when the daemon says so", revisit the threshold (see [[#Future considerations & optimizations|Future considerations]]).

## Future considerations & optimizations

Forward-looking. None of these block Phase 5 burn-in (Tuesday).

### Reconciler refinements

- **Frigate `record.enabled: true` couples to ORPHAN noise.** The 6h floor papers over the deeper issue: Frigate always records, so ORPHAN can never truly mean "recording happened without daemon bookkeeping." Two ways to make ORPHAN actionable:
  1. Have the daemon own Frigate's `record.enabled` — toggle it true only when a session is active. Investigated before and rejected — toggling `record.enabled: false` breaks Frigate; off-limits as a fix. Not on the table.
  2. Track daemon uptime in the WAL ([[#Architecture / wiring|see below]]); compute ORPHAN as "Frigate segments during daemon-up periods with no overlapping session." Cleaner, no Frigate-side risk. Decide after a week of reconciler observation.
- **STUCK rule's `EXPORT_BEGIN` requirement is fragile.** Backfilled rows are excluded today, but if the WAL is ever truncated to disk pressure, recent `EXPORT_BEGIN` could disappear before its `EXPORT_COMPLETE`. Add a soft fallback: if a session has `START` + `EXPORT_BEGIN`-shaped sidecar file (e.g. `_session.json` exists with `export_status: in_progress` for > 24 h) but no WAL pair, still flag STUCK. Lower priority.
- **DEGRADED loses signal under long sessions.** A 2-day Diane session with one 30 s stall is currently `DEGRADED`. That's noisier than useful. Refine to a duration-relative rule: `total_stalled_seconds / wall_duration > 0.001` (≥ 1 s of stall per 1 000 s recorded). Implement after first organic DEGRADED finding.
- **Reconciler doesn't (yet) check that `EXPORT_COMPLETE.payload.moved_to` files actually exist on disk.** Lower-cost than re-walking the export tree but worth adding once we see a single false-positive `EXPORT_COMPLETE`. Two lines of `os.path.exists` per row.

### Architecture / wiring

- **Persist daemon uptime windows in the WAL.** Add a `BOOT` event on `start()` and a `SHUTDOWN` event in the stop path. Useful for the smarter ORPHAN rule above and for diagnosing "when was the daemon up" outside `journalctl --since`. Trivial — one column reuse.
- **Reconciler findings as WAL rows.** Currently findings live only in memory + MQTT. Persisting them — say, a new `findings` table or a `RECONCILE` event type — would give us the same crash-safety guarantee the lifecycle events have. Decide after 1-week observation: if findings are stable at 0 per night, the in-memory plus MQTT path is enough.
- **`STATE_DEFER_SECONDS = 1.5` is empirical.** Today's restart sequence runs all messages within the same wall-clock second, so 0.5 s would likely suffice. 1.5 s is a comfortable margin. If the user clicks Record and is surprised the recording takes 1.5 s to "appear" anywhere, document the tradeoff or drop to 0.5 s — easy revert.
- **`FrigateController._pending_state_actions` is per-camera.** Two distinct restarts within 1.5 s would collapse into one cancelled set, which is the right behavior — the second restart subsumes the first. Documented in `_schedule_state_callback`'s docstring.

Decide between `truncate -s 0` (5 s, may break a `tail -f` consumer if any) or a logrotate config that the radiens client logger honors. Worth a 5-min investigation Monday.
