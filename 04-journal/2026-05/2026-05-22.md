  ```yaml
  image: eclipse-mosquitto:2@sha256:9cfdd46ad59f3e3e5f592f6baf57ab23e1ad00605509d0f5c1e9b179c5314d87
  ```

  Uses the locally-cached image directly; no Docker Hub roundtrip needed. **The SHA digest is the right pin for any image that doesn't publish per-patch tags.** Worth remembering for future pins.

## Phase 1.3 — Mosquitto password auth

Generated a 24-char URL-safe random password: see [[../../00-config/production-values#Mosquitto MQTT Authentication (since 2026-05-22)|production-values.md]].

**Found a code gap:** the daemon's `FrigateController` constructor accepted `mqtt_host`/`mqtt_port` but no user/password. Made a minimal change in two files:

```python
# backend/frigate_controller.py — __init__ signature
mqtt_user: Optional[str] = None,
mqtt_password: Optional[str] = None,
# backend/frigate_controller.py — connect_mqtt() right before connect()
if self.mqtt_user:
    self._mqtt_client.username_pw_set(self.mqtt_user, self.mqtt_password)
# backend/daemon.py — FrigateController instantiation
mqtt_user=config["mqtt"].get("user"),
mqtt_password=config["mqtt"].get("password"),
```

Backwards-compatible: when user is empty/None, behavior is unchanged from anonymous-connect. Committed as `2f7365d`.

Files updated in the maintenance window:

- `/srv/frigate/mosquitto/passwd` — generated via `docker exec mosquitto mosquitto_passwd -c -b /tmp/passwd nvr <secret>` (host's `/usr/bin/mosquitto_passwd` doesn't exist; only inside the mosquitto container).
- `/srv/frigate/mosquitto/mosquitto.conf` — `allow_anonymous false` + `password_file /mosquitto/config/passwd`.
- `/srv/frigate/config/config.yml` — added `mqtt.user: nvr` + `mqtt.password: <secret>`.
- `/opt/neurosurveillance/config.yaml` — added `mqtt.user`/`mqtt.password`.

**First boot failed.** Mosquitto refused to load `passwd` (created mode 600) because the in-container `mosquitto` user (UID 1883) couldn't read a file owned by host UID 1000. Container kept restart-looping at 26 s intervals. Fix: `chmod 644 /srv/frigate/mosquitto/passwd` + `docker restart mosquitto`. Now Mosquitto warns about world-readable + non-mosquitto ownership ("Future versions will refuse to load") — cosmetic; the bcrypt-style hash is not sensitive on disk. **Real fix for later:** `sudo chown 1883:1883 /srv/frigate/mosquitto/passwd && sudo chmod 0700 ...`.

## Phase 1.4 — Coordinated restart cycle

Order: `systemctl stop neurosurveillance-session` → `docker compose down` → (May 18 residue cleanup landed here) → `docker compose up -d` → `systemctl start neurosurveillance-session`.

**Critical finding — the 2026-05-20 startup-guard regression reproduced cleanly.** Sequence:

1. 19:24:51 — Frigate started fresh (`record.enabled: true` in config); ffmpeg came up over the next ~90 s.
2. 19:25:17 — Mosquitto crash-looping (bad `passwd` perms, not yet fixed).
3. 19:25:17 — Daemon started; tried to connect MQTT; Mosquitto unavailable.
4. 19:27:02 — Mosquitto stable after `chmod 644`.
5. 19:27:04 — Daemon connected to MQTT (`u'nvr'` — auth working).
6. 19:27:04 — Daemon subscribed to `frigate/+/recordings/state`.
7. **19:29:00** — Frigate's full subsystem reached steady state and published current ON state to all four `frigate/{cam}/recordings/state` topics (about 4 min after Frigate started; matches Frigate's typical post-init delay).
8. Daemon saw `(was None) -> ON` for all four cameras. Treated as legitimate transitions. Spawned four phantom `ManualSession` records.
9. 19:29:47 — Watchdog (May 18) fired `STALL` for all four cameras with lag 181–191 s, because the daemon believes recordings are active but no segments are being written (Frigate's own daemon-initiated `Turning off recordings` at 19:26:42–49 had already stopped the real recording).
10. User noticed the Frigate UI showing recordings active, clicked "stop" — but those clicks went into Frigate's UI **without producing a state transition the daemon could see**, because Frigate's "set recording" idempotency means a stop on a camera Frigate already considered "OFF" doesn't republish to `recordings/state` with retain.
11. Daemon's `manual_recordings` still held the four phantom sessions at the time of the API check ~10 min later.

**Diagnostic value:** this exact 11-step timing chart is the test scenario the [[../../07-decisions/2026-05-stabilization-sprint-week-1-plan#Phase 3 — Sunday: startup guard fix + nightly reconciler (council Stage 2.2)|Phase 3.1 fix]] needs to make pass. The fix proposal (subscribe to `frigate/available` LWT, re-arm grace on `offline→online`) closes step 8 specifically — the LWT would have been `online` at 19:24:51 and stayed online through the regression; the grace re-arm at the right boundary would have suppressed the spurious 19:29 ON transitions.

## Cleanup of phantom sessions

Decision recorded in chat: manually clean phantoms tonight, defer the code fix to Sunday Phase 3. Approach:

```bash
# Publish OFF (retained) for all 4 cams — daemon sees ON→OFF, runs stop_recording
for cam in pi_cam_0 pi_cam_1 pi_cam_2 pi_cam_3; do
  docker exec mosquitto mosquitto_pub -h 127.0.0.1 -u nvr -P <secret> \
    -t "frigate/${cam}/recordings/set" -m "OFF" -r
done
```

Each `stop_recording()` call:

1. Captured session end time (~19:55) → duration ≈ 1570 s.
2. Wrote session JSON (`/opt/neurosurveillance/sessions/2605221929_manual_pi_cam_{0,1,2,3}_session.json`) with `mouse_id: "manual"`, `user_name: "manual"`, `recording_type: "pi_cam_X"`.
3. Triggered Frigate export for the 19:29 → 19:55 window. **Frigate rejected the request** — segments only exist for 19:24:51 – 19:26:48 (before the session window started). Status set to `"failed: export request rejected"`.
4. **No orphan files in `/srv/frigate/storage/exports/`** — clean failure path. Frigate rejected the request before creating any work product.

Deleted the four JSONs:

```bash
rm /opt/neurosurveillance/sessions/2605221929_manual_pi_cam_{0,1,2,3}_session.json
```

Daemon state back to `manual_recordings: {}`.
