## The 11 "deviant" segments were a false alarm

```
    150 frames : 5377 segments  <-- EXPECTED
    165 frames :   11 segments  <-- LONG (+15 frames, keyframe-boundary cut, harmless)
```

165 frames = 11 s = exactly one extra GOP given `--intra 15` (one keyframe per second). That is ffmpeg's segment muxer cutting on a later keyframe: it re-partitions frames, it does not lose them.

⚠️ **`frame_integrity_check.py` had a bug on its first run** and reported "FRAMES ARE BEING LOST". It computed a single net deficit as `sum(expected - actual)`, which goes negative on a surplus. Worse, the netting meant 11 long segments could have cancelled 11 genuinely short ones and read as clean. Fixed so only SHORT segments and PTS gaps count as loss, and long segments are reported separately.

## Built: the daemon fix

Implements decision items 2-4 of [[2026-07-27-video-eeg-sync-recording-architecture]].

> [!warning] THE NEW CODE IS ALREADY ON THE DEPLOYED PATH — it activates on the next restart, planned or not
> `/opt/neurosurveillance/session-daemon` is a **symlink** to `~/Monitoring_project/neurosurveillance/backend`, so editing the repo edits the deployment. The running process still holds the OLD code in memory (it started 2026-07-17 13:28 and Python loads source once), so live behaviour is unchanged **until the service restarts**.
>
> **That restart is not necessarily yours to schedule.** A crash, a reboot, or an `apt` upgrade will load the new code. There is no staging step here.
>
> Production `/opt/neurosurveillance/config.yaml` has **no `recording:` block**, which is fine: the code defaults are `drain_seconds=30` and `reset_on_start=false`, exactly what the block would set. The block was added to the repo reference copy `config/config.yaml` only.

### Recording is now a refcounted LEASE, not a boolean

```
enabled = (manual_lease OR session_lease)
```

`frigate_controller.py` gains `acquire_lease` / `release_lease` / `adopt_lease` / `has_lease` / `lease_holders`. Nothing outside that section may call `set_recording(enabled=False)` any more; callers release their own lease and the LAST release turns recording off. This makes it structurally impossible for an EEG session to stop a recording a human started.

### 30 s drain before the last release

`daemon.py:447` used to publish OFF immediately on `R_ON → R_OFF`, then export. Frigate's maintainer then unlinked whatever was still in `/tmp/cache`. Now the drain and the lease release happen inside the export thread, BEFORE the export runs, so the segments covering the end of the session are on disk first.

Worst case in flight is 10 s (segment period) + 5 s (flush interval) = **15 s**, so 30 s is 2×. **Not a tuning knob.**

### FAIL-ON at shutdown

`stop()` no longer publishes OFF at all, and no longer calls `stop_all_recording()`.

> A camera left recording is recoverable. A lost tail, or a whole run lost to a RETAINED OFF, is not.

This is the fix for the failure that made a 72 h run record ZERO video. It logs loudly which cameras were left running. A shutdown landing mid-drain also aborts the drain and leaves recording ON.

### Startup no longer stomps recordings in progress

Startup used to publish OFF to every camera as a "clean slate", which would cut short any run already going. It now reads runtime state from `/api/config` and ADOPTS whatever is already recording as a manual lease. `recording.reset_on_start: true` restores the old behaviour.

⚠️ **This is the least-tested part of the change**, because the startup grace-period logic below it was written assuming that OFF gets published.

### Files

- `backend/frigate_controller.py` — lease model, `DEFAULT_DRAIN_SECONDS`, `get_cameras_recording()`
- `backend/daemon.py` — lease call sites, fail-ON shutdown, non-stomping startup
- `backend/tests/test_recording_leases.py` — **12 behavioural tests, all passing**, no MQTT or Frigate needed
- `config/config.yaml` — new optional `recording:` block (defaults match the code)

### What the drain does NOT fix

**Manual recordings stopped from the Frigate UI still lose their tail.** The UI publishes OFF before the daemon ever sees it, so the segments are already gone. Only the daemon-controlled path can be drained. Mitigation stays operator habit: stop ~30 s after the interesting part.
