> A KAIST lab is building a mouse sleep-EEG/EMG rig: NeuroNexus XDAQ + Intan RHD2216 headstages, Allego/Radiens software, on an ASUS mini-PC (Intel Ultra 5 125H, Ubuntu 24.04). Claude Code has been the primary troubleshooting engine for ~2 weeks, driving the work + writing an Obsidian vault + Python analysis scripts. Critically analyze the current state and history, and define a good CHECKPOINT to continue from. Key facts supplied: the multi-day enumeration mystery (root cause = dead top SPI socket); the chip-identity flip-flop (RHD2132→RHD2216); grounding root-caused to "animal had no ground tie"; the 2-mice-per-headstage flip-flop (yes→no); the stale `2mice32` map in `xdat_io.py`; the fragile 2-venv split; the SDK impedance crash; only one 4.5h EEG-only recording (A1, EMG open); rig declared electronically validated with per-animal electrode contact as the stated remaining limiter.

## Advisor responses (verbatim)

### The Contrarian
The confidence that "only the surgical quality remains" is the most dangerous belief in this whole file.

**The channel map bug is live and unacknowledged.** `xdat_io.py` has a `2mice32` CHANNEL_MAP commented "validated 2026-07-01: impedance sweep good." The actual 2026-07-01 verdict was the opposite — one headstage per mouse, shared GND bus invalidated. That comment is factually wrong and nobody fixed the code. The next multi-mouse recording processed through that script will silently assign channels to the wrong animal. There is no git history to catch when this was written or what it assumed.

**The "bipolar chip + software bipolar derivation" is unresolved.** RHD2216 is described as a bipolar chip with hardware differential inputs. The analysis scripts then do `native_0 − native_1` in software. These are not the same operation and one of them is wrong or redundant. If the chip is already outputting a differential signal, software subtraction doubles the derivation. Nobody has explicitly reconciled this. The one "clean" EEG result doesn't prove the derivation is correct — it proves the noise floor is low enough that the error didn't matter yet.

**A 72h run has no crash resilience.** Allego forgets everything on restart: mode, 1kHz rate, channel selection. A single headstage bump (which already happened once) requires manual intervention to restore. There is no watchdog monitoring allegoserver, no auto-reconnect, no alert if the session silently stops mid-night. The daemon monitors Frigate and video; it does not monitor whether Allego is still actually writing data.

**MEMORY.md is truncated.** At 33KB vs 24KB limit, part of it did not load into Claude Code's context. The retractions and corrections — the most critical information — are at the top of recent entries. There is no guarantee the next session inherits the corrected mental model rather than an older wrong one.

**One recording is not validation.** It is an existence proof with broken EMG. The "rig is validated" claim requires demonstrating clean EEG AND EMG simultaneously on a properly implanted mouse, sustained through a full sleep cycle. That has never happened.

### The First-Principles Thinker
The stated problem is "make the rig work." The actual problem is "produce publication-quality 72h multi-mouse sleep-stage data." These are not the same problem, and the last two weeks have been solving the wrong one.

Here is what the history actually shows: every technical mystery (enumeration, railing, chip identity, grounding) was ultimately resolved by reading the hardware documentation more carefully or by physical inspection. No mystery required Claude Code. Claude Code did not accelerate those resolutions — it generated and propagated wrong hypotheses (RHD2132, cold joints, wrong mode as root cause) that cost days. The vault is not a knowledge asset; it is a changelog of retracted theories.

The real objective has three sub-problems, none of which are primarily electronics:

**1. Surgical reliability.** Every mouse has one clean EEG leg and one or more open-circuit EMG or EEG legs. The rig is electronically validated but you have zero fully-instrumented animals. The bottleneck is surgical technique: electrode placement, insulation stripping, suturing, connector cleanliness. No amount of Python scripting changes this.

**2. Recording endurance.** You have one 4.5h session. You need 72h. You do not know yet whether your setup sustains signal across that duration. Connector contact drift, animal movement, and slip-ring wear are unknowns with zero data.

**3. Scoring pipeline.** You have EDF output. You don't have a validated scorer-to-publication pipeline. The IIIS scorer opened the file — that's it.

The checkpoint question you should be asking is not "where did we leave off technically?" It is: "What is the minimum viable experiment that produces one scoreable 72h 2-state (EEG + EMG) trace from one fully-implanted mouse?" Everything else — multi-mouse scaling, xdat_io maps, venv splits — is premature until that exists.

The rig is not the bottleneck. The surgery is.

### The Expansionist
The Radiens SDK integration is the most undervalued asset here. The ability to programmatically pull live signal snapshots and read gate states isn't just a QC convenience — it's the nucleus of a fully automated sleep-staging pipeline. One step away: wire `get_signals` into a rolling classifier that calls a lightweight model (TinySleepNet or YASA) every 30 seconds and publishes wake/NREM/REM state to MQTT. The video NVR already subscribes to that bus. You now have timestamped behavioral video automatically labeled by sleep stage — a product most sleep labs pay tens of thousands of dollars for in commercial systems.

The XDAT-to-EDF pipeline is publication-grade infrastructure disguised as lab tooling. It already imports into the IIIS scorer. Package it with the Obsidian vault's grounding protocol and impedance checklist and you have a reproducible methods supplement that other RHD2216/XDAQ labs worldwide would adopt immediately. There is no open-source, validated, end-to-end XDAT→EDF→scorer pipeline publicly available. This is it.

The 64-channel dual-headstage + planned 8-mouse C3442 scale-up is not a single lab's rig anymore — it's a colony-scale acquisition system with synchronized video. At 8 mice simultaneous, with automated staging and behavioral video correlation, this crosses the threshold into phenotyping infrastructure. That's a core facility offering. Other groups at KAIST would pay for access. Granting agencies fund "shared resource" infrastructure differently than single-lab equipment.

The session daemon + MQTT + Frigate integration already abstracts hardware away from the experimenter. The hidden bet: this stack generalizes to any tethered biosignal + behavioral camera setup, not just mouse EEG. Rat LFP, primate EMG, insect locomotion — the architecture is already agnostic. The vault documents the pattern, not just the instance.

### The Outsider
The most glaring thing: **the AI is leading the debugging, not assisting it.** For two weeks, a language model that cannot touch hardware, cannot see signals, and cannot smell a bad solder joint was the primary diagnostic engine. Every dead-end chase — wrong chip model, wrong grounding theory, nearly shipping hardware back to the vendor — happened because a text predictor was reasoning about a physical system it cannot observe. The humans appear to have deferred to the AI's hypotheses rather than anchoring each step to measurable evidence first.

The "validated" label on a contradicted setting is not a minor nit. It means the documentation actively misleads. If one label is wrong, how many others are? Large, cross-referenced documentation with inline corrections is not a knowledge base — it is an archaeology site. A fresh person cannot trust any single entry without tracing its correction chain.

Two Python environments to run one analysis pipeline is a dependency management failure, not a workflow. This will bite every new lab member and every future upgrade.

The "2 mice per headstage" flip-flop is a sign that conclusions were being drawn from incomplete experiments and committed to documentation before they were solid. The AI wrote theory, the humans tested, the test was ambiguous, the AI revised theory — but the cycle moved faster than the evidence warranted.

One usable recording after two weeks, missing half its channels due to a surgical fault that was not caught before the animal was implanted, suggests the verification checklist before surgery was either absent or ignored.

The outsider question: **who is responsible for each decision?** Right now it looks like the AI decides and the humans implement. That inversion should be named and fixed before week three.

### The Executor
**Monday morning: three actions before the surgery happens.**

**Action 1 (30 min): Fix xdat_io.py now.** The "2mice32" map tagged "validated 2026-07-01" is factually wrong — the day's actual verdict was one mouse per headstage. That map sitting in the pipeline with a false validation date will corrupt any future 2-mouse analysis and poison the paper. Open the file, rename the map to `DEPRECATED_2mice32_DO_NOT_USE`, add a comment with the date and why, commit it. Do this before any recording touches the pipeline.

**Action 2 (4 hours): Thermal stress test before surgery.** 90°C at 1 mouse is a ceiling problem, not a marginal problem. Plug in 2 headstages today (64ch), run a 4-hour continuous recording, log temps with `sensors` every 60s. If it throttles at 2 mice, you need a cooling fix (USB fan, better case airflow, or offload processing to another machine) before you implant 4-8 animals. Don't do surgery until you know the real thermal limit. This is the fastest way to find out if your 8-mouse goal is physically possible on this hardware.

**Action 3 (1 hour): Surgery checklist, written and printed.** The EMG failures are all implantation faults. Write a 10-item pre-closure checklist: DMM continuity on every electrode pin before closing, EMG tip insulation stripped and confirmed in muscle belly, ground pin DMM-beeped to bus, impedance sweep GUI (Allego paused) before leaving OR. Print it. Tape it to the OR bench. Every mouse gets checked off before closure.

**What's NOT blocking:** The Allego state-loss is annoying but solved by a laminated startup card — 15 minutes to make. The venv split is real but can wait until post-surgery.

**First step Monday at 9am:** Open xdat_io.py.

## Peer review round (3 reviewers, anonymized)

All three independently crowned the **Contrarian** the strongest response (only one to name a live, actionable bug), and all three flagged the **Expansionist** as the biggest blind spot (pricing commercial upside on an unvalidated base). Each surfaced a *different* gap the whole council missed:

- **Reviewer 1 — slip-ring wear = the silent 72h killer.** The hand-soldered custom slip-ring rotates continuously for 72h under mouse locomotion. Nobody asked its rated rotation lifetime or whether contact resistance drifts over a multi-hour run. A ring that reads clean at t=0 and degrades to high-Z by t≈36h produces a recording that looks valid in the morning and is unusable by the next day — with no automated detection.
- **Reviewer 2 — animal triage / 3Rs before committing to surgery.** Every response assumed more implants are the next step. None asked whether each already-implanted mouse should be scored against a minimum-viable threshold (clean EEG + working EMG + passing 72h impedance stability) *before* new surgery. Implanting more mice into an unvalidated pipeline wastes animals — an IRB/3Rs constraint the council never touched.
- **Reviewer 3 — 3am operator coverage.** All diagnostic knowledge lives in Claude's session context and a vault that is not in an actionable form for a sleep-deprived student at 3am when a headstage drops mid-72h session. No response asked: who recovers a dropped recording at 3am, with what printed checklist, and what does "recovery" even mean for a partially-written xdat set with no checksum? That gap is more likely to kill a 72h run than any electronics issue.

## Chairman verdict (synthesis)

**Where the council agrees:** (1) "Validated" is false — one 4.5h EEG-only recording is an existence proof, not validation. (2) The bottleneck is surgery + endurance, not electronics. (3) The `2mice32` map was a live bug (now fixed). (4) The AI ran ahead of the evidence — real resolutions came from hardware docs / physical inspection, not AI hypotheses; going forward the human owns the physical/measurement call. (5) A 72h run has zero crash resilience — no watchdog on whether Allego is still writing.

**Where the council clashes:** the Expansionist alone argues the real value is the upside (auto-stager, open pipeline, colony-scale facility); all three peer reviewers called that premature on an unvalidated base. First-Principles ("stop, reframe to one scoreable 72h trace") vs Executor ("do 3 concrete things before surgery") is a sequencing tension, not a real conflict — Executor is *how* you start First-Principles' plan.

**Blind spots caught only in peer review:** slip-ring wear over 72h; animal triage / 3Rs before more surgery; 3am operator recovery with no checksum on xdat; hardware-vs-software bipolar unreconciled; MEMORY.md truncation dropping corrections from the next session.

**Recommendation:** Stop treating this as "rig done → scale to 8." Freeze scaling, commercialization, and C3442/8-mouse work until the minimum-viable bar is met: **one fully-instrumented mouse producing a scoreable 72h 2-state (EEG + EMG) trace.**

**The one thing to do first:** Before any new surgery, run a single 2-headstage / 64-ch continuous endurance test (aim 24h+, min 4h) logging `sensors` temp every 60s AND slip-ring/contact stability over time — while fixing the `xdat_io.py 2mice32` map. This one test answers thermal survival, contact/slip-ring endurance, and unattended Allego stability at once. Fail here = learn it with wires, not with implanted animals and a burned 72h experiment.
