## Work Log

### Fixed: Can't delete exported video recordings

**Problem:** Exported videos in `/srv/frigate/storage/exports/` were undeletable. The daemon organized exports into `{user}/{mouse}/{date}/` subdirectories inside the Docker volume, but all directories were root-owned (created by `sudo mkdir -p`). Linux requires write permission on the parent directory to delete files, so even chowned MP4s were trapped.

**Root cause:** The config set `export_dir` to `/srv/frigate/storage/exports` (Docker volume, root-owned), using it as both the Frigate source and organized target. The `chown -R` call in `daemon.py` silently failed because sudoers didn't allow the `-R` flag.

**Fix applied:**
1. Separated source and target paths in `daemon.py`:
   - `export_source_dir`: `/srv/frigate/storage/exports` (Frigate Docker volume, read-only)
   - `export_dir`: `/opt/neurosurveillance/exports` (skimlab-owned, user-deletable)
2. Replaced `sudo mkdir -p` with `Path.mkdir()` (no sudo needed -- target dir is skimlab-owned)
3. Removed broken `chown -R` call
4. Updated `config.yaml` with new `export_source_dir` key
5. Updated sudoers: removed `mkdir` from allowed commands
6. Moved existing exports from Docker volume to `/opt/neurosurveillance/exports/` and chowned

**Files changed:**
- `neurosurveillance/backend/daemon.py`
- `config/config.yaml` + production copy on NVR
- `/etc/sudoers.d/neurosurveillance-fs` on NVR
- Vault: `architecture.md`, `production-values.md`

> [!warning] Correction added 2026-08-14 — steps 2, 3 and 5 above are NOT true of the deployed code
> Verified on the NVR today: `daemon.py:665` still calls `sudo mkdir -p`, `daemon.py:667` still calls `sudo chown -R skimlab:skimlab`, and `sudo -l` still lists both `mkdir` and `chown` as NOPASSWD. Exports do land correctly, so nothing is broken — but the "replaced with `Path.mkdir()`" / "removed broken `chown -R`" / "removed `mkdir` from sudoers" claims describe an intent that was never deployed.
>
> Step 6 was also incomplete: 18 pre-fix files (39 G, Feb 12 – Mar 6) were left behind in `/srv/frigate/storage/exports/`, still `root:root` inside a `root:root drwxr-xr-x` directory, so `skimlab` could not delete them. See [[../2026-08/2026-08-14]].

### Changed: Metadata now gates recording (only chambers with metadata record)

**Problem:** When Radiens started EEG recording (`R_OFF → R_ON`), the daemon started Frigate recording on **all 4 configured cameras** regardless of whether metadata was set. Chambers without metadata got `"unknown"` placeholders in filenames -- wasting disk and creating junk recordings for unused chambers.

**Fix applied:**
1. Added `pending_metadata_is_default()` method to `SessionManager` -- checks if a chamber has real metadata or just defaults
2. `_handle_session_start()` in `daemon.py` now filters `chambers_to_start` to only include chambers where metadata was explicitly set via GUI/API
3. If no chambers have metadata when Radiens starts, a warning is logged and no video is recorded

**Behavior change:**
- **Before:** All 4 cameras record when Radiens starts, regardless of metadata
- **After:** Only cameras tied to chambers with metadata set will record

**Files changed:**
- `neurosurveillance/backend/session_manager.py` -- added `pending_metadata_is_default()`
- `neurosurveillance/backend/daemon.py` -- filtered chamber selection in `_handle_session_start()`
- Vault: `architecture.md` (design principles, state machine, pseudocode)
- Vault: `session-recording-workflow.md` (quick reference, steps, multi-chamber section, metadata callout)

### Verified: Camera-to-chamber mapping correct for all 4 cameras

Traced the full pipeline for chambers 0–3. Each camera ID (`pi_cam_0` through `pi_cam_3`) is correctly matched end-to-end:
- Config key (`chamber_0` → `pi_cam_0`) → used for Frigate MQTT toggle and export API
- MQTT wildcard `frigate/+/recordings/state` catches all cameras independently
