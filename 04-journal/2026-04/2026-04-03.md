## Work Log

### Overnight Temperature Alerts — Root Cause & Fix

After killing `allegoserver` yesterday (~18:12), Netdata continued alerting overnight. Investigation showed:

- `allegoserver` was **not running** — confirmed via `pgrep`
- RAPL power cap was **never applied** — still at 200W (uncapped)
- Baseline temperature 68–74°C from normal load (4x FFmpeg QSV + Frigate + GNOME + RustDesk + containerd)
- Brief transient spikes touched 75°C every 20–40 min, keeping the `nvr_cpu_temperature` alarm in WARNING (hysteresis threshold)
- Alarm finally cleared at 08:07 when temp dropped below 75°C for 5+ minutes

**Not the same problem as yesterday** — yesterday was allegoserver busy-polling (87–92°C spikes). Today was the system's normal thermal baseline being too close to the 75°C hysteresis threshold due to the uncapped RAPL.

### RAPL Power Cap Applied

Applied the fix from yesterday's incident doc:

```bash
echo 20000000 | sudo tee /sys/class/powercap/intel-rapl/intel-rapl:0/constraint_0_power_limit_uw
```

Created persistent systemd service: `/etc/systemd/system/cpu-power-cap.service`

```bash
sudo systemctl enable --now cpu-power-cap.service
```

**Result after reboot:** CPU package dropped to **58°C** (from 68–74°C baseline). 17°C headroom before the 75°C hysteresis threshold. Overnight alerts should stop.

Updated [[03-troubleshooting/incidents/2026-04-02-allegoserver-thermal-spikes|incident doc]] status to `resolved`.

## Notes

- RAPL = Running Average Power Limit (Intel's CPU power budget mechanism). 20W cap matches the NUC's cooling capacity. No real-world performance impact — video encoding uses QSV (GPU), not CPU.
- Uptime Kuma has no unauthenticated REST API. Must use `docker exec uptime-kuma sqlite3 /app/data/kuma.db` for programmatic queries (sqlite3 not installed on host).
- Netdata data retention appears to be ~24h at full resolution, with longer retention at lower resolution. Historical queries beyond 24h may return averaged data.
