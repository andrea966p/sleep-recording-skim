## Work Log

### Recovery verification

After restarting the daemon from recovered source files, two additional gaps were found and fixed:

**Gap 1 — `api.py` storage endpoints (second-order recovery, commit `423e8f5`)**

Daemon crashed immediately on restart:
```
TypeError: init_api() got an unexpected keyword argument 'storage_monitor'
```

Root cause: the transcript used for recovery was from **2026-04-01**. Storage endpoints were added **2026-04-02** and not captured by the replay script. The replay logic anchors on the most recent full Read, then applies subsequent Edits — but adding entirely new routes (not edits to existing code) left no trace. The `api.pyc` mtime was also Apr 2, which would have flagged this if checked against the baseline.

Recovered by reconstructing from the `StorageMonitor` interface + the response shape captured from the live process before restart. Added:
- `GET /api/storage` — full disk status from `StorageMonitor.get_status()`
- `GET /api/storage/estimate?num_cameras=N` — hours/days of recording headroom
- `GET /api/storage/camera-bitrates` — go2rtc reachability + per-camera bitrates
- Updated `GET /api/health` to include `storage_level` + `storage_used_percent`

**Gap 2 — export rename used wrong source path (commit `920378a`)**

Discovered during the test recording: both cameras' exports completed at Frigate level but no files appeared in `/opt/neurosurveillance/exports/`. Log showed:
```
WARNING: Export file not found on disk for renaming: /opt/neurosurveillance/exports/pi_cam_0_...mp4
```

Root cause: `_move_export_file` in `daemon.py` built `source_path` from `export_dir` (`/opt/neurosurveillance/exports`) — the *destination* — instead of `export_source_dir` (`/srv/frigate/storage/exports`) — where Frigate actually writes. This was a pre-existing bug in the committed code at HEAD `40b0330`, not introduced by recovery.

Fix: store `export_source_dir` from config on the daemon, pass it explicitly to `_move_export_file` as a distinct parameter from `export_dir`.
