### Frigate / neurosurveillance daemon — export path issues
Full writeup: [[2026-04-08-frigate-export-stuck-and-missing-on-edges]]

- Discovered `pi_cam_0` and `pi_cam_1` had been recording continuously since 2026-04-06 ~07:02 UTC. **Not a docker update** (container up since 04-03, RestartCount=0). Root cause: the Pi at `192.168.0.11` was offline until 04-06 16:02 JST — frigate auto-resumed recording as soon as RTSP was reachable. Need to be aware of this on next Pi boot.
- Stopped `pi_cam_2` / `pi_cam_3` manually from Frigate UI at 18:02 → **no auto-export**. Reason: the daemon's manual-session callback (`_handle_external_recording_change`, `daemon.py:441`) never saw an OFF→ON transition for those cams on MQTT, so there was no open ManualSession to close. The raw segments are still in `/media/frigate/recordings/...` and can be exported manually.
- Radiens / Allego disconnected (`446110 consecutive` poll failures). This kills the Radiens-driven auto-export path but NOT manual-session detection — daemon is alive (pid 4518) and the manual path is armed.
- Manual short-recording test on cam_0/cam_1/cam_2 → cam_1 and cam_2 exported fine, **cam_0 Frigate export stuck `in_progress=true`** with no ffmpeg worker and no output file. Daemon timed out cleanly after 300 s (`Export pi_cam_0_nhjty7 timed out`). Workaround: `DELETE` the orphan export, re-POST, then manually `mv`/`chown` into `/srv/frigate/storage/exports/manual/manual/2026-04-08/`. All 3 files now present.
- Follow-ups: investigate Frigate orphan-export race, seed ManualSessionManager from `/api/config` at daemon startup so pre-existing enabled cams aren't invisible, fix the stale `/opt/neurosurveillance/logs/daemon.log` (frozen at 2026-02-26).
