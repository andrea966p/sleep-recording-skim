## Work Log

### Cam 1 "zoomed" investigation

Compared vault docs, live Frigate config, and Pi stream metadata.

**Findings:**

- Pi-side go2rtc stream definitions were symmetric (`1024x768`, `15fps`, same bitrate/codec flags)
- RTSP probe confirmed both source streams were `1024x768`
- Frigate runtime had a mismatch: `pi_cam_0` detect path at `1024x768`, `pi_cam_1` detect path at `1280x720`
- This mismatch explains the apparent zoom/crop/aspect distortion in Live view

### Frigate parity fix applied

Updated `/srv/frigate/config/config.yml` with explicit detect dimensions for both cameras:

```yaml
cameras:
  pi_cam_0:
    detect:
      enabled: false
      width: 1024
      height: 768
  pi_cam_1:
    detect:
      enabled: false
      width: 1024
      height: 768
```

Restarted Frigate container and verified:

- `/api/config` shows both cameras detect at `1024x768`
- `/api/stats` ffmpeg detect pipelines both `w=1024:h=768`
- latest snapshots for both cameras returned `1024x768`

### Documentation sync

Updated vault infra doc to match deployed config:

- `01-infrastructure/frigate/config-yml.md` updated to include explicit detect width/height (`v5.2` state)

### Camera label attempts (unsuccessful on current Frigate build)

Goal: show chamber/camera names in the Live interface.

Attempts made:

1. **Per-camera `name` field**
   - `name: Chamber 0/1` failed config validation (spaces disallowed)
   - `name: chamber_0/chamber_1` passed validation but caused Frigate backend crash (`KeyError: 'pi_cam_0'`) on this build
   - immediately rolled back

2. **`camera_groups` approach**
   - groups appeared in API config but did not provide the expected on-tile labels in the current UI path

3. **Per-camera `timestamp_style.format` chamber prefixes**
   - applied to force visible labels on-frame
   - later removed at user request during outage response

### Outage during session: Pi became unreachable again

After the above rounds, Frigate started reporting no frames.

**Observed from ASUS/Frigate host (`192.168.0.50`):**

- ffmpeg errors: `No route to host` for `rtsp://192.168.0.11:8554/pi_cam_0` and `pi_cam_1`
- `ping 192.168.0.11` -> `Destination Host Unreachable`
- ARP neighbor for Pi IP showed `INCOMPLETE`
- direct go2rtc API check to Pi (`192.168.0.11:1984`) unreachable

This indicates L2/L3 reachability loss to the Pi (power/link/network path), not a Frigate parser failure.

### Revert executed (user requested)

Reverted all label-related Frigate changes from `/srv/frigate/config/config.yml`:

- removed per-camera `timestamp_style`
- removed `camera_groups`
- kept only the earlier safe detect-dimension parity fix (`1024x768` for both cameras)

Frigate config validates and container is healthy, but streams remain down because Pi is unreachable.

Also reverted the vault Frigate doc from label variants back to parity-only state (`v5.2` content).

### Recovery check after on-site power cycle (next morning)

After manual Pi power cycle, recovery validation from ASUS host showed full service restoration:

- `ping 192.168.0.11` successful (`0%` packet loss)
- `curl http://192.168.0.11:1984/api/streams` returned both stream entries with active consumers from Frigate host
- `ffprobe` on both RTSP streams returned `1024x768 @ 15fps` H.264
- Frigate `/api/stats` returned `~5.1 fps` ingest for both cameras
- Frigate latest snapshots for both cameras are `1024x768`

Observed transient startup behavior:

- Shortly after reboot, Frigate logs showed temporary `Connection refused` to `192.168.0.11:8554`
- This transitioned to stable ingest once go2rtc and camera producers came fully online
