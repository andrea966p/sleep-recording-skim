### Export Corruption Bug — `wait_for_export` Race Condition

**Symptom:** A 19-hour manual recording (~15 GB) was corrupted and unplayable after export.

**Root cause:** Frigate's `/api/exports` endpoint lists an export immediately when requested, even while the background `ffmpeg` process is still multiplexing the file. The export entry is flagged with `"in_progress": true` during processing.

Our `wait_for_export()` method in [[architecture|frigate_controller.py]] was not checking the `in_progress` flag. It saw the export appear in the list, assumed completion, and immediately executed `sudo mv` to rename and move the file. Because `ffmpeg` was still writing, and MP4 files store the critical `moov` atom (file index/header) at the very end of the file, the moved file was left without a valid header — making the entire 15 GB file unplayable.

**Fix:** Patched `wait_for_export()` to check `export.get("in_progress", False)`. If the flag is `True`, the method continues polling instead of returning. The export is only considered complete when it appears in the list with `in_progress` absent or `False`.

```python
# Before (broken):
for export in exports:
    if eid == export_id:
        return export  # BUG: returned while still in_progress

# After (fixed):
for export in exports:
    if eid == export_id:
        if export.get("in_progress", False):
            break  # Keep polling — Frigate still processing
        return export  # Safe — file is fully written
```

**Impact:**
- The corrupted 15 GB file in `/manual/` is unrecoverable (no `moov` atom = no seek table)
- All future exports (both Radiens and manual) are now safe
- Daemon restarted after patch deployment

**Lesson:** Frigate's export API is asynchronous — the export list is not a completion signal. Always check the `in_progress` flag before touching the file.
