## Phase 2.1 — `backend/session_journal.py`

New module. The contract is intentionally narrow so the daemon paths that already exist can wire it in without restructure.

| Surface | Responsibility |
|---|---|
| `SessionJournal(db_path)` | Opens the DB, applies `journal_mode=WAL`, `synchronous=FULL`, `temp_store=MEMORY`, creates `events` table + 3 indexes (`ts`, `session_id`, `(event_type, ts)`) |
| `log_event(event_type, session_id, camera, mouse_id, payload, ts)` | Appends one row. Returns `bool`. Never raises. |
| `query(since, until, event_type, session_id, limit)` | Read-side. Newest-first, bounded by `limit` (default 500, cap 5000). |
| `count_by_type(since)` | Aggregate counts for dashboards / `/api/journal`. |
| `close()` | Idempotent. |

Event type constants live in the module (`EVENT_START`, `EVENT_EXPORT_BEGIN`, `EVENT_EXPORT_COMPLETE`, `EVENT_ABORT`, `EVENT_STALL`) and `VALID_EVENT_TYPES` is enforced at the `log_event` boundary — any unknown string returns `False` rather than corrupting the journal.

**Durability:** WAL mode + `synchronous=FULL` fsyncs the WAL file on every commit. Even an OS-level crash between two recordings can lose at most an uncommitted statement (and we commit per `INSERT` because `isolation_level=None`).

**Concurrency:** one `sqlite3.Connection` guarded by `threading.Lock`. SQLite's serialized threading mode lets us share that connection across the API thread, the export thread, the watchdog thread, and the main loop without a connection pool. The lock is held briefly (single `execute` per event).

**Failure policy:** all errors are logged and swallowed; the journal never raises into the recording path. Callers that need fail-closed behavior (Phase 2.2 manual START) check the returned `bool`.

## Phase 2.2 — START wiring

| Location | Behavior |
|---|---|
| `manual_session_manager.start_recording()` | **Fail-closed.** Build session record → call `journal.log_event(START, …)`. If the write returns `False`, return `None` instead of an in-memory session. |
| `daemon._handle_external_recording_on()` | New `None` check. Publishes `OFF` back to `frigate/{cam}/recordings/set` to undo Frigate's in-progress recording so nothing keeps spinning without a journal entry. |
| `session_manager.start_session()` | **Fail-open.** Radiens already started — we can't refuse. Log the journal failure and continue. |
| `session_manager.abort_session()` | Emits `ABORT` with `reason` + `duration_seconds` payload. Fail-open. |

The two managers carry different policies because the failure modes are different: a manual recording can be un-done (publish `OFF`), a Radiens recording cannot (Radiens is the source of truth, our recording is the dependent variable).

## Phase 2.3 — EXPORT_BEGIN / EXPORT_COMPLETE

Wired in `daemon._execute_export()` rather than inside `frigate_controller` itself, because:

1. The daemon owns the session object that carries `session_id`, `mouse_id`, `video_filename`, and the user/mouse/date target path. `frigate_controller` is a lower-level adapter and shouldn't grow a session vocabulary.
2. Both Radiens and manual exports go through the same `_execute_export` helper, so one wiring covers both.

The control flow now reads as: `START` (manager) → `EXPORT_BEGIN` (pre-POST) → Frigate export → wait → `EXPORT_COMPLETE` (post-move, includes the final disk path).

To capture the move target, `daemon._move_export_file()` now returns `Optional[Path]` (the destination on success, `None` on failure). The `EXPORT_COMPLETE` row carries `moved_to` as a payload field so the reconciler can verify the MP4 actually exists where the daemon says it does.

## Phase 2.4 — STALL wiring

The recording watchdog ([[2026-05-18|May 18 work]]) was already publishing MQTT alerts at `neurosurveillance/watchdog/{cam}/stall`. Today it also writes a `STALL` row to the journal.

To make the row useful for the reconciler, the watchdog now gets a second optional provider — `active_sessions_provider: () → dict[camera, session_id]` — implemented by `daemon._active_session_ids()`. This means a STALL event is annotated with the `session_id` that was running at the moment lag exceeded `STALL_THRESHOLD` (60 s by default). Without it, the reconciler would have to guess which session a stall belongs to from timestamps.

MQTT payload also gained the `session_id` field — useful when Slack wiring lands in [[../../07-decisions/2026-05-stabilization-sprint-week-1-plan#Phase 4 — Monday: code quality + remaining ops|Phase 4.1]].

## Phase 2.5 — `GET /api/journal`

Filters: `since` / `until` (epoch float), `event_type` (one of the five constants), `session_id`, `limit` (default 500, cap 5000). Response shape:

```json
{
  "count": <int>,
  "counts_by_type": {"START": 49, "EXPORT_COMPLETE": 45, "ABORT": 4, "EXPORT_BEGIN": 1},
  "events": [ {ts, event_type, session_id, camera, mouse_id, payload}, ... ]
}
```

`counts_by_type` honours the `since` filter so a frontend can show "events in the last 24 h grouped by type" with a single call. The endpoint is wired through `init_api(session_journal=…)` in `daemon.py` so the API thread re-uses the same `SessionJournal` instance the recording paths write to.

## Phase 2.3b — Exponential Radiens backoff (promoted from May 1 council)

The trigger: `/opt/neurosurveillance/radiens.log` had grown to **3.2 GB** by the time we restarted the daemon. Two `ERROR - grpc_error - … StatusCode.UNAVAILABLE` lines per second came from the radiens client library's own logger every time `_client.get_status()` was called and Radiens wasn't running. The daemon's main loop calls `poll()` once per 1 s, and the previous `connect()`/`poll()` pair issued one wire call each on every tick.

Backoff bounds:

```python
BACKOFF_BASE   = 1.0
BACKOFF_FACTOR = 2.0
BACKOFF_MAX    = 60.0
```

Both `connect()` and `poll()` now consult `self._next_attempt_at` before touching the wire. On failure, `_on_failure(now)` advances `_next_attempt_at` and doubles `_backoff` (clamped to `BACKOFF_MAX`). On the first successful call, `_on_success()` resets everything to base.

`ImportError` (radiens package structurally missing) is treated as permanent — `_next_attempt_at = float("inf")` — so a misconfigured venv stops producing log lines instead of one every poll cycle. The existing "log every 5th consecutive failure" behavior is preserved; the warning string now also reports the next-attempt delay so log readers can see the backoff escalating.

Local test verified the contract: a `FakeClient` whose `get_status()` always raises produced 1 wire call across 5 `poll()` invocations within a 1-second window, then the next failed call advanced the backoff to 4 s.

The 3.2 GB existing log file is **not** auto-truncated by this change — the backoff stops further growth but the historical spam stays. Carried into Phase 4 cleanup (see [[#Operational / cleanup|Operational / cleanup]] below).

## Phase 2.7 — Backfill

`backend/scripts/backfill_journal.py` reads `*_session.json` from `/opt/neurosurveillance/sessions/`, replays each session as a synthetic `START` + closing event (`EXPORT_COMPLETE` if `export_status == "completed"`, otherwise `ABORT`), and skips any `session_id` already present in the WAL (idempotent).

Run results: `seen=49 wrote=48 skipped_old=0 skipped_dup=1 errors=0`. The skipped row was today's smoke-test session — the live wiring had already journaled it.

Post-backfill aggregate (`GET /api/journal?limit=1`):

```json
{
  "ABORT": 4,
  "EXPORT_BEGIN": 1,
  "EXPORT_COMPLETE": 45,
  "START": 49
}
```

The 4 `ABORT` rows correspond to the [[2026-04-08-frigate-export-stuck-and-missing-on-edges|Apr 8 stuck exports]] (3 × Diane's `H5S251A_*_monitoring` sessions on 2026-05-07 and 1 × `2604081838_manual_pi_cam_0`). All `export_status: "failed"` strings map to `ABORT` via `classify_end()`.

Backfilled events all carry `payload.backfilled: true` so the reconciler can recognise them and apply looser thresholds (no `EXPORT_BEGIN` exists, so "EXPORT_BEGIN with no COMPLETE within 24 h → STUCK" must skip backfilled rows).

## Future considerations & optimizations

These are forward-looking. None block Sunday. Most should be re-evaluated **after** the reconciler runs for a few nights — many of these will either be answered by reconciler findings or proven unnecessary.

### Architecture / design

- **WAL rotation / retention.** Today the journal grows unbounded. With ~5 events per session and Diane's current cadence (~3 sessions/day × 365 = ~5500 events/year ≈ a few MB/year) this is harmless for the foreseeable future. But the reconciler joins WAL against Frigate's `recordings` table, and Frigate purges recordings on `retention_days`. Once retention crosses (default 7 d) the reconciler will see WAL rows that Frigate no longer has — these are "ORPHAN by retention" not "ORPHAN by bug" and need a separate classification. Decision deferred until reconciler is live.
- **Cross-machine durability for the WAL.** Council [[../../07-decisions/2026-05-stabilization-sprint-week-1-plan#Open questions (not blockers)|open question]] from May 20. The WAL is on the NVR's NVMe; if the NVMe dies, the WAL dies. Two options: (1) Syncthing-replicate `session_wal.db` (must use SQLite `.dump` snapshots — Syncthing copying an open WAL DB risks corruption); (2) `sqlite3 .backup` via cron to a second disk or NAS. Tailscale NAS reachability is still the precondition for option 2.
- **EXPORT_BEGIN coverage on backfill.** Backfilled rows have `START + EXPORT_COMPLETE/ABORT` but no `EXPORT_BEGIN`. The reconciler rule "EXPORT_BEGIN > 24 h without COMPLETE → STUCK" must skip rows where `payload.backfilled == true`. Document this explicitly in `reconciler.py` so future me doesn't tighten the rule and accidentally flag all historical sessions.
- **Journal write atomicity vs Frigate state.** The current fail-closed path (`start_recording` returns `None` → daemon publishes `OFF`) creates a tiny window where Frigate may have recorded ~1-2 segments before the `OFF` lands. Those segments will appear as `ORPHAN` to the reconciler (no `START` exists). Consider a daemon-side rule: ORPHAN segments shorter than `(_handle_external_recording_on round-trip estimate)` are not flagged. Or: only emit the journal write **after** confirming Frigate's ON echo. Decide once reconciler shows the actual ORPHAN rate.

### Operational / cleanup

- **`/opt/neurosurveillance/radiens.log` is 3.2 GB.** The backoff fix stops further growth but doesn't reclaim the existing file. Two options: `truncate -s 0 /opt/neurosurveillance/radiens.log` (fastest, breaks any external tail consumers) or `logrotate` config that the radiens client's logger honors (cleaner, more work). The radiens package writes to that file via its own logger config — `logger.handlers` on `radiens` package modules. Worth a 5-min investigation before deciding.
- **Mosquitto `passwd` file permissions.** [[2026-05-22#Phase 1.3 — Mosquitto password auth|Carried from yesterday]]: currently `chmod 644` because Mosquitto refused to read the file at `600`; the real fix is `chown 1883:1883` + `chmod 0700`. Lands in Monday Phase 4 cleanup.
- **Sprint plan mention of "council 2.3 lock on `_last_known_state`" is open.** `frigate_controller._on_message` mutates `_last_known_state` and `_expected_states` from the MQTT thread; everything else reads them from the API / main thread. The `_expected_lock` already covers `_expected_states`. `_last_known_state` is currently raced — read in the same function but not held under a lock. Race window is tiny (one assignment), but adding a second `Lock` is cheap and removes the surprise. Worth folding into Phase 3.1 since we'll be touching the file anyway.

### Reconciler enhancements (Phase 3.3 — opportunistic)

- **Use the journal `EXPORT_COMPLETE.payload.moved_to` as ground truth for "where the MP4 actually is" instead of recomputing the path.** The session JSON sidecar already carries `video_filename` but not the user/mouse/date prefix. Today the reconciler would need to re-derive the path; tomorrow it can read it directly. Saves a `pathlib` walk per session.
- **`STALL` rows carrying `session_id`** (added today) let the reconciler classify a session as "completed but stalled mid-recording" — a `START` + `STALL` + `EXPORT_COMPLETE` triple. The current proposed buckets (`ORPHAN` / `PARTIAL` / `STUCK`) don't model this. Add a fourth bucket — `DEGRADED` — for sessions that completed export but had at least one stall during recording. Useful for the researcher's QC pass.
- **`payload.backfilled: true`** — the reconciler should report backfill coverage separately. Helpful in week 1 so we can tell "the WAL has 49 sessions, of which 48 are backfilled and the truth-source for those is the JSON sidecar, not the live wiring".

### Observability

- **Surface `journal_last_event_age` in `/api/health`.** [[../../07-decisions/2026-05-stabilization-sprint-week-1-plan#Functions to reuse (don't recreate)|Sprint plan reuse note]] called this out. If `now - last_event_ts > 7 days` and we have active sessions, something is silently broken. Cheap to add to the existing `/api/health` handler. Skipped today because the only call site was a placeholder.
- **Netdata alert on WAL file size or row count.** A runaway loop that emits one `STALL` per second would inflate the WAL. Alarm at, say, > 1000 events/hour. Same Netdata pattern as the `nvr_dockerd_restart` rule from [[2026-05-21#0.3 — Netdata docker-daemon restart alert|May 21]]; ~30 min to set up.
- **Frontend journal viewer.** Not in scope for this sprint — but the API is now in place. A simple read-only list (events table with session_id grouping) would give the researcher a chronological view next to `SessionHistory`. Trivial follow-up once Phase 4 lands.

### Radiens backoff follow-ups

- **Watchdog the watchdog.** If backoff caps at 60 s and Radiens never recovers, we'll attempt once a minute forever and log every 5th miss. That's fine. But if Radiens comes back after, say, 2 hours, we have 2 hours of "is Radiens up yet?" attempts to skip; the first successful one detects the new ON/OFF state immediately. Today's transition-detection logic (`previous_state == OFF → ON`) handles this correctly because `_previous_state` is left untouched on failure. Validated by reading the code; no regression.
- **No backoff jitter.** All daemons starting at the same time would synchronize their backoff attempts. We have exactly one daemon per machine so this is non-issue, but worth a one-line comment in `radiens_poller.py` for future-me.
- **Radiens client logger is independent of ours.** The radiens client's own logger writes to `/opt/neurosurveillance/radiens.log`. We can't fully silence it from Python without poking at its handlers. The backoff is the right layer; suppressing the radiens client logger is wrong (would also hide real errors when something is genuinely broken).
