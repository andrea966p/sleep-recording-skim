### External Analysis Review

Reviewed a comprehensive analysis comparing the vault's golden configs against official RPi camera documentation and go2rtc upstream docs. The analysis covered go2rtc exec source behavior, rpicam-vid options on Pi 5, Frigate integration patterns, and systemd service configuration.

**Key finding from the research:** Pi 5 has **no hardware H.264 encoder**. It uses software encoding (x264 via libav). The golden config rules table incorrectly said "Direct hardware encoding" -- fixed.

**Key finding from RPi docs:** Three rpicam-vid flags were missing from the production config:
- `--low-latency` -- suppresses B-frames on Pi 5 (software encoder generates B-frames by default, which can break streaming clients)
- `--intra 15` -- sets keyframe interval to 1 second (default was 60 frames = 4 seconds at 15fps). Frigate recommends 1x GOP for fast stream startup.
- `-n` -- disables preview window (useless on headless Pi, wastes resources trying to render to nonexistent display)

**What the analysis got right:**
- Part 1 (validations): H.264 path, single-line exec, `KillMode=control-group`, direct stdout, TCP transport, QSV decoding all confirmed correct
- Part 3 (things to avoid): H.265, ffmpeg pipes, gpu_mem ineffectiveness all confirmed

**What the analysis got wrong:**
- Suggested replacing `ExecStartPre=/bin/sleep 60` with systemd dependencies -- rejected because the 60s delay is for **hardware/electrical** reasons (IR LED power spike prevention during boot), not software timing
- The "hardware encoding" label in the rules table (contradicted its own findings)

### Core Technical Concepts Learned

1. **Pi 5 software encoding:** Pi 5 has no dedicated H.264 hardware encoder (unlike Pi 4). The `--codec libav` path uses x264 software encoding via ffmpeg/libav backend. This is why CPU usage is higher than expected and why `--low-latency` exists specifically for Pi 5.

2. **B-frames on Pi 5:** The software encoder generates B-frames by default (Pi 4's hardware encoder did not). B-frames improve compression but cause issues with streaming formats. `--low-latency` suppresses them and also disables arithmetic coding, trading slightly worse compression for significantly better streaming compatibility.

3. **Keyframe interval matters for Frigate:** The default `--intra 60` meant a keyframe every 4 seconds at 15fps. Frigate must wait for a keyframe to start decoding. Setting `--intra 15` (= 1 keyframe/second) dramatically improves stream startup time and recovery after network glitches. Frigate docs explicitly recommend matching GOP to framerate.

4. **go2rtc pipe transport:** go2rtc's exec source reads H.264 bitstream (or MPEG-TS) from stdout via pipe transport. It also supports `#starttimeout=N` parameter (added in v1.9.14) and `#killsignal=N` / `#killtimeout=N` for process lifecycle management.

5. **MPEG-TS vs raw H.264:** Raw H.264 bitstream lacks container-level framing and timestamps. MPEG-TS wraps the stream with proper packet boundaries and timing info. RPi docs recommend MPEG-TS for all streaming scenarios. This is worth testing but should not be changed in production without validation.

### Watchdog Setup on Pi

Set up three-layer monitoring on `192.168.0.11`:

| Layer | Mechanism | Handles |
|-------|-----------|--------|
| systemd `RuntimeWatchdogSec=30s` | Hardware watchdog via `/dev/watchdog` | Kernel hangs — auto-reboot |
| systemd `Restart=always` (go2rtc service) | Service-level restart | go2rtc process crashes |
| `watchdog.sh` cron (every 5 min) | Custom monitoring script | go2rtc down, API unresponsive, runaway CPU/memory |

**Steps completed:**
1. Configured systemd watchdog in `/etc/systemd/system.conf` (`RuntimeWatchdogSec=30s`, `RebootWatchdogSec=10min`), applied with `daemon-reexec`
2. Disabled `watchdog` daemon package — conflicts with systemd (both claim `/dev/watchdog`, `errno 16 Device or resource busy`)
3. Created `/home/skimlab/watchdog.sh` monitoring script (checks go2rtc service, rpicam-vid CPU, go2rtc memory, API responsiveness)
4. Added cron: `*/5 * * * * /home/skimlab/watchdog.sh`

**Key decisions:**
- **Removed 4h periodic restart** (`0 */4 * * * sudo systemctl restart go2rtc`) — incompatible with continuous 24/7 recording. Each restart kills streams for ~60s due to `ExecStartPre=/bin/sleep 60` IR LED safety delay. Unacceptable data loss for mouse sleep research with concurrent EEG/EMG.
- **Removed `watchdog` daemon** — systemd's `RuntimeWatchdogSec` provides identical kernel-hang protection without the `/dev/watchdog` conflict.

**Vault doc updated:** `watchdog-monitoring.md` rewritten to reflect systemd-only approach with warning against installing the watchdog daemon.

### Persistent Journal Fix (FINAL)

**Second Pi crash occurred during lunch** — one camera stream had been open in browser for 1h40m (idle viewing), then SSH dropped and Pi became unreachable (pingable but sshd not responding). Same pattern as 2026-02-10 crash.

**Root cause of missing logs:** Raspberry Pi OS ships with `/usr/lib/systemd/journald.conf.d/40-rpi-volatile-storage.conf` which forces `Storage=volatile` (RAM-only, wiped on reboot). This overrides `/etc/systemd/journald.conf` settings.

**Fix:**
```bash
# Create higher-priority drop-in config
/etc/systemd/journald.conf.d/99-persistent-journal.conf
[Journal]
Storage=persistent
SystemMaxUse=500M
```

The `99-` prefix overrides the `40-` default. Journal now persists across reboots at `/var/log/journal/`, capped at 500MB to protect SD card.

**Verification:**
```bash
systemd-analyze cat-config systemd/journald.conf | grep Storage
# Shows: Storage=persistent (last)
journalctl --disk-usage
# Shows: 8M on disk
```

Next crash will finally have diagnostic logs via `journalctl -b -1`. Full incident: [[2026-02-11-persistent-journal-fix|Persistent Journal Fix]]

### VSCode Remote Crash Diagnosis (RESOLVED)

**Problem:** After deploying v5.1, tested system with both camera streams active in browser. All CPU cores maxed at 100%, system became unresponsive.

**Initial hypothesis:** Camera streams consuming excessive CPU due to software encoding.

**Actual cause:** VSCode Remote background indexing. `top` output revealed:
```
  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
 2527 skimlab   20   0  169820  94564  36428 R 190.9   2.3   8:28.97 rg
 2528 skimlab   20   0  169820  94388  36352 R 181.8   2.3   8:15.09 rg
 2407 rpicam+   20   0  222068  87932  20620 S  12.8   2.2   0:29.67 rpicam-vid
 2412 rpicam+   20   0  220568  85808  20004 S  12.7   2.1   0:30.02 rpicam-vid
```

Two `rg` (ripgrep) processes from VSCode Remote consumed **~372% CPU combined** (190.9% + 181.8%), while camera processes only used **~25% combined** (12.8% + 12.7%).

**Resolution:** Closed VSCode Remote. The `rg` processes terminated automatically. CPU returned to normal:
- CPU: 7.0% user, 93.0% idle
- Camera processes: 18.2% each (~36% combined)
- Temperature: 58.2°C (no throttling)

**Root cause of crashes:** VSCode Remote's resource-intensive background file indexing starved the system. sshd couldn't accept new connections while under extreme CPU load from indexing, but existing SSH connections remained alive (explaining the "pingable but sshd refuses connections" symptom).

**Key lesson:** VSCode Remote is unsuitable for resource-constrained camera nodes. Use lightweight editors (nano/vim) or edit remotely via MCP filesystem server.

Full incident: [[2026-02-11-vscode-remote-cpu-exhaustion|VSCode Remote CPU Exhaustion]]
