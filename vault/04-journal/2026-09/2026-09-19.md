# 2026-09-19 — The ThinkPad joined the push/pull workflow, driven from e10

## TL;DR

The ThinkPad is now set up and in sync, and it was done **entirely over SSH from
`e10ubuntu`**, without sitting at the laptop. Getting that remote access working took
most of the effort; the setup itself was one missing setting.

Three things worth carrying forward:

- **The only real gap on the laptop was a missing git identity.** Everything else — the
  clone, all nine Claude Code symlinks, a correct `settings.json` with hooks — was
  already right. But `git config user.name` was empty, so the first `./skim push` would
  have failed.
- **Syncthing is gone from the ThinkPad too**, so it is now retired on every machine. The
  2026-09-16 write-up saying the ThinkPad still had it is out of date.
- **Enabling Tailscale SSH on a machine silently breaks the ordinary key based SSH into
  it.** That is what briefly killed `ssh e10` from the laptop, and the cause is not
  obvious from any error message.

### The one thing that was actually broken

```
$ git config user.name
$ git config user.email
$
```

Empty, at every level. `./skim push` commits before it pushes, and `git commit` refuses
without an identity, so the first attempt to send work back would have failed with an
error about the machine's identity rather than anything to do with this workspace. Set
to `andrea966p <andrea96p@kaist.ac.kr>`, matching the other machines.

🔑 **A machine that passes `check.sh` and `skim status` can still be unable to push.**
Neither command looks at the git identity.

✅ **Fixed the same day: `./skim check` now has a third section that checks it** and exits
non-zero when it is missing, printing the two `git config --global` commands. Both branches
were exercised, the failing one in a throwaway repository rather than by unsetting the real
identity. Worth knowing while reading it: on `e10ubuntu` the identity lives in the repo's
own `.git/config`, not in `~/.gitconfig`, so `GIT_CONFIG_GLOBAL=/dev/null` does not simulate
the missing case there.

## Getting in at all

The laptop had **no sshd**: `connect to host 100.66.98.20 port 22: Connection refused`.
It was always the client in this setup, reaching into `e10ubuntu`, never the other way.
Tailscale SSH was not enabled either.

### The tailnet policy will not let one user SSH to another user's node

Enabling Tailscale SSH on the laptop was not enough:

```
tailscale: tailnet policy does not permit you to SSH to this node
```

The default policy only allows SSH between machines owned by the **same** user
(`autogroup:self`). `e10ubuntu` belongs to `skimlab.kaist@gmail.com` and the ThinkPad to
`andrea.piazzola4@gmail.com`, so nothing matched.

The obvious fix — a rule with the other user as the destination — is rejected outright:

```
HTTP 400  {"message":"users in dst are only allowed from the same user"}
```

⭐ **An SSH rule's destination can only be `autogroup:self` or a TAG.** Never another
user's login. Crossing owners therefore *requires* tagging the destination machine.

### Tagging costs something, and it is not reversible by accident

The ThinkPad now carries `tag:thinkpad`, owner `autogroup:admin`. What that changes:

- the tag owns the device, not `andrea.piazzola4@`, so it drops out of every
  `autogroup:self` rule
- tagged devices do not expire their keys
- applying the tag can force the device to re-authenticate, so **do it while you can still
  reach that machine**

The working rule, saved through the console's visual SSH rule builder:

| Field | Value |
|---|---|
| Source | `skimlab.kaist@gmail.com` |
| Destination | `tag:thinkpad` |
| As destination user | `autogroup:nonroot` |
| Check mode | **Off** |

⚠️ **Check mode must be Off.** "Check" demands a browser re-authentication per session.
That is fine for a person and blocks any unattended use completely.

### The tailnet policy cannot be edited from the CLI

`tailscale` 1.102.4 has no ACL or policy subcommand; the only non-browser route is the
HTTP API, and the API needs an access token that can only be minted in the admin console.
Being logged in on a node gives no admin authority — node auth and admin API auth are
separate.

The API is still the gentler path when the visual editor is confusing: mint a token,
`GET /api/v2/tailnet/-/acl` (ask for `application/hujson`, or the comments come back as
blank space), edit, `POST` it back with `If-Match` on the ETag. Read the token from a
0600 file rather than pasting it into a command line. It is a live credential: delete
the file and revoke the token in the console afterwards, since deleting the file alone
revokes nothing.

## The trap: Tailscale SSH quietly replaces your real sshd

Earlier in the session `sudo tailscale set --ssh` was run on **`e10ubuntu`** by mistake,
meaning to run it on the laptop. It appeared harmless. It was not.

Once the ThinkPad was reachable, `ssh e10` **from the laptop** — a path that had worked
for weeks on a key already in `~/.ssh/authorized_keys` — returned:

```
tailscale: tailnet policy does not permit you to SSH to this node
```

Two changes from the same afternoon combined:

1. **Tailscale SSH on `e10ubuntu` makes `tailscaled` intercept port 22 for tailnet
   peers.** The real sshd is bypassed entirely, so the key never gets a chance.
2. **The ThinkPad had just become tag-owned**, so its identity is `tag:thinkpad` and the
   default `src: ["autogroup:member"]` rule no longer matches it.

Fixed with `sudo tailscale set --ssh=false` on `e10ubuntu`, which hands port 22 back to
the real sshd. `ssh e10 'hostname && tmux -V && docker ps'` from the laptop then answered
immediately.

🔴 **Turning on Tailscale SSH is not additive. It takes over port 22 for tailnet traffic
and your existing authorized_keys stop mattering.** On a machine that already has working
key based SSH, leave it off.

## Where SSH stands now

| Direction | Mechanism |
|---|---|
| `e10ubuntu` → ThinkPad | Tailscale SSH, via `tag:thinkpad` and the rule above |
| ThinkPad → `e10ubuntu` | ordinary sshd and an ed25519 key, `Host e10` in `~/.ssh/config` |

The two use completely different machinery, which is worth remembering when one of them
breaks and the other does not.
