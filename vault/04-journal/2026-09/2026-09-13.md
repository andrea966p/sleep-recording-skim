## The 24 h recording got through, after three fixes

The ZT0-to-ZT0 run of 2026-09-12 (`allego_0__uid0912-08-55-18`, 8 mice, 90.8 GB, 24.065 h)
reached the NAS: stripped 93.18% smaller to 6.24 GB, bit-exact, **5 files VERIFIED**. The
original is untouched. **Five of eight animals pass rung 2** over the full 24 h, which
matches the best full-cohort result this rig has produced.

It took three fixes to get there, and all three were my design errors rather than anything
wrong with the recording.

**A new mouse id blocked a 24 h recording.** The QC stage demanded a hand-written cohort
manifest and these eight animals were a new batch. Andrea's objection was exactly right:
mouse ids are arbitrary labels people invent constantly, so why is one a blocker.
`cards/ladder.py:676` settles it —

    spec = C.CohortSpec(roles=tuple(cohort.roles))

— the QC computation takes **one** thing from a manifest, the role list `["eeg","emg"]`.
Everything else labels the cards. And the console already knew the roles (from the preset)
and the identities (from the slots). It had everything and asked for it again in another
format. It now generates the manifest itself; verified to reproduce the hand-written one
exactly, and in 47 s instead of 5 min because the feature cache is reused.

**Gate B refused a 90 GB strip over 1 ms of noise.** It refused to drop any digital input
that was not perfectly constant. `din_1` had 2 transitions: a single 1 ms blip 2.43 h in,
flat for the other 23.99 h, on an input with nothing plugged into it. A camera pulse at
15 fps would be ~1.3 million transitions. The gate now counts, and refuses on ≥ 4
transitions or a level held off-resting for over a second; anything smaller is recorded with
exact counts and does not block.

**Dates came from UTC on a rig that runs on KST.** An 08:55 KST start is 23:55 UTC the
previous day, so the run was filed as `2026-09-11_allego_0__uid0912-08-55-18`, contradicting
the uid in its own filename. The uid is already local, so it is now the source.

## The scheduler works, and the bench test earned itself

First scheduled run on the real rig, a deliberate 9 minutes:

    11:20:03  SCHEDULED  -> STARTING   3 s after the instant
    11:20:10  STARTING   -> RECORDING  growth confirmed, 2.86 GB/h
    11:29:00  RECORDING  -> STOPPING   0.5 s late
    11:29:02  STOPPING   -> STOPPED

And then nothing. `worker.submit()` existed **only on the HTTP stop endpoint**, so a
scheduled stop halted the rig correctly and then stranded the run at STOPPED — no QC, no
strip, no upload — until the service happened to restart. Silent, and it would have hit the
first unattended overnight run. Both stop paths now go through one `on_stopped` callback.

After the fix the stranded run completed and exercised the **auto-computed QC bundle** for
the first time: no manifest, no human step, 5 files verified.

## Later: one question found two more defects

Andrea asked something nobody had asked: *should the other presets be tested, and what
happens if we put only four or five mice in instead of eight?*

Partial occupancy itself was already right — the preset resolves labels from the occupied
slots, so three mice in `A1 C2 D1` give a six-channel file. Stripped a real recording that
way to check rather than to assert: bit-exact, reads back as exactly those six labels.

Two things behind it were not right.

**A four-mouse run was graded on eight positions.** `cards/ladder.py` falls back to
`spec.positions()` — every slot the *layout* has, not every slot the *operator* filled.
Dropped five animals from the 24 h S-SL manifest and ran it:

    A1    HLBSSL31         2    PASS  PASS  PASS
    A2    UNKNOWN@A2       1    PASS  PASS  FAIL
    B1    UNKNOWN@B1       2    PASS  PASS  PASS
    B2    UNKNOWN@B2       2    PASS  PASS  PASS
    C1    UNKNOWN@C1       2    PASS  PASS  PASS

On a genuinely empty slot those cards are built from floating amplifier inputs. Three of
them read **PASS at rung 2**, which is the problem: the output is not self-evidently noise,
it looks like an animal somebody forgot to name. The QC step now passes `--positions` from
the run's occupied slots. The floor itself was never at risk — floor sites are `/3`–`/16`
and `/35`–`/48`, which no slot occupies — so this only removes false cards.

**`unipolar_lfp` could not finish the pipeline at all.** Its sites are `/18`–`/23` on
32-channel ports; `CohortSpec` derives the floor as `base+n`–`/16` on a 64-channel chip, so
no floor exists and `roles_for_preset` returns `None`. The chain then asked the operator to
override the missing-bundle guard on **every** unipolar run. The refusal was correct — a
floor computed there would measure animals against the wrong control sites — but demanding
a per-run override for it was not. A guard that can never be satisfied is a guard people
learn to click past, including on the runs where it is load-bearing.

A preset now declares `qc: none`. The chain records `qc_not_applicable`, deliberately a
different key from `qc_bundle_skipped`: *no criterion exists for this layout* and *a person
waived the check* must not be confusable a year from now. `presets.py` refuses a site-based
preset that fails to declare it, so the next one cannot inherit the same dead end quietly,
and the console states it under the slot grid before the run rather than in a failure after.

## Third ask: give the recording a name

Andrea asked for a text field so a run is filed under its batch, not under the
acquisition box. The shape they specified:

    20260925_HLBSSL_RSR/20260925_HLBSSL_RSR_8mice_data.xdat
    YYYYMMDD  _ batch _ BSR|RSR|SDR  _ Nmice

Straightforward, and it works — typed into the console it previews live, and the
API returns exactly that for the example given. Four things the request did not
settle, decided and written into `naming.py` next to the code rather than in a
commit message nobody will find:

**Mixed conditions.** One run covers all four ports, so a basal animal and an sd
animal can share it. Every code present is joined in config order,
`20260925_HLBSSL_BSR-SDR`, rather than picking one and filing half the animals
under a condition they were not in. Refusing the run instead would repeat the
mouse-id blocker: stopping an experiment over a naming detail.

**The rename is remote only.** The local stripped copy keeps its Allego name,
because the strip is resumable and idempotent on exactly that name. Renaming
locally would make a re-run look like a new file. Nothing is lost: the stripped
sidecar's `dataset_provenance` already carries the source base, its uid and both
source hashes, and `run.json` travels in the same folder.

**The QC bundle keeps its own name.** Those features describe the full
262-channel original, not the stripped copy. Naming them after the copy would
invite exactly the wrong reading.

**The folder name is frozen on the run** at the first upload attempt. The
collision rule takes the next free name; running it on every attempt would walk
an interrupted upload into a fresh folder each time and leave partial copies
behind, each looking like a separate recording.

## The preview caught a disagreement between two buttons

With the field wired up, the console previewed `20260914_HLBSSL_BSR` — tomorrow —
on a form filled in today. Not a bug in the date code: **Start at** is pre-filled
with the next 09:00, and it was already 13:52. So a scheduled run and a
**Start now** run genuinely carry different dates, and the preview had quietly
picked one. It now shows both when they differ.

Worth noting the shape of that: the feature was correct, and the *preview of the
feature* is what exposed the ambiguity. Showing people what the machine is about
to do is not only a courtesy to them.

## And the test that wrote to production

Writing the upload test, I pointed `nas_upload.MANIFEST` at a temp file and ran
it. It went to the real one anyway — `manifest_load(path=MANIFEST)` binds the
path as a **default argument at import time**, so assigning the module constant
afterwards does nothing. Eight rows landed in
`eeg-recorder/deploy/uploads.jsonl` claiming files were VERIFIED on the NAS that
had never been uploaded.

That is not a cosmetic mess. The uploader **skips** files it finds VERIFIED
there, so a later real run named `20260925_HLBSSL_RSR` would have uploaded
nothing and reported success. Removed the eight rows; the manifest is back to 22
entries covering exactly the four folders that really exist on the share. The
path is now late-bound and `EEG_UPLOAD_MANIFEST`-overridable, and the hazard is
written into the NAS procedure page with the one-line check for it.

I caught this because the second test run failed with two files missing, and the
reason was that the first run had already recorded them as done. If the test had
passed both times I would have committed it and left the rows there.
