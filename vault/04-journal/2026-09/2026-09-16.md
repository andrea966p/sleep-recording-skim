# 2026-09-16 — Syncthing off e10ubuntu and the office PC, and a fourth machine

## TL;DR

Syncthing is now **gone from `e10ubuntu` and from the office PC**, packages and all. It
had been dead since the single repository cutover on 2026-09-10, so removing it moved no
data and broke nothing. `skim check` is green on both. **Only the ThinkPad still has it**,
and it has nothing left to talk to.

Neither device identity was thrown away. Both are parked at
`~/syncthing-config-retired-2026-09-16` on their own machine.

A **fourth machine** joined the same evening, the SKIM office workstation at
`/home/skim/sleep-recording-skim`. Two things worth carrying forward came out of it: a
`bootstrap.sh` run can report success while leaving a machine with **no SessionStart
hooks**, and `sudo apt autoremove` offered to delete a working NVIDIA driver stack on one
machine after doing nothing harmful on another.

## Why this was safe

Before touching anything I read what Syncthing on this machine actually held. Two
folders were configured and both were already empty shells:

| Folder in the configuration | Path | State on disk |
|---|---|---|
| `default` | `~/Sync` | empty, only the `.stfolder` marker |
| `Monitoring Project Obsidian Vault` | `~/Monitoring_project/Monitoring_project_obsidian_vault` | **path does not exist any more** |

The vault now lives inside the one repository at
`~/sleep-recording-skim/vault/` (149 MB), which is why the old path is gone. The
daemon was not running, `syncthing@skimlab.service` was disabled, the user level
`syncthing.service` was disabled, and nothing was listening on ports 8080, 22000 or
21027. Only the tray icon process `syncthingtray` was alive, and a tray icon is a
graphical client for a daemon that was not there.

So there was nothing to lose. Worth saying plainly anyway, because it is the thing
people get wrong about package removal: **`apt purge` removes the program and its
files under `/etc`. It never touches your home directory and it never deletes synced
files.** A peer that vanishes does not cause deletions on the other machines either.
Syncthing only propagates a deletion when a device that still shares the folder
deletes the file.

## What I actually ran

1. `pkill -x syncthingtray` and deleted `~/.config/autostart/syncthingtray.desktop`
2. `sudo apt purge syncthing syncthing-gtk syncthingtray` — 28.0 MB freed
3. `sudo apt autoremove` — 13 orphaned libraries, mostly the Qt5 WebEngine bundle
   that `syncthingtray` had dragged in, 165 MB freed
4. Removed the dead leftovers: the configuration pin drop in at
   `~/.config/systemd/user/syncthing.service.d`, the empty `~/Sync`, and the stale
   second configuration directory `~/.local/state/syncthing.STALE-DO-NOT-USE`
5. **Moved**, not deleted, the live configuration:
   `~/.config/syncthing` → `~/syncthing-config-retired-2026-09-16`

Step 5 is the only judgement call. That directory holds this machine's device
identity `2LNSMIM-T2IHNXN-...` and its certificates. Delete it and a future
reinstall would appear to the office PC and the ThinkPad as a brand new device that
has to be re accepted from scratch. Keeping it costs 40 KB.

Two things that were part of the Syncthing setup went away on their own with the
purge: `syncthing-resume.service`, the system unit that sent a HUP after a suspend,
and the configuration directory pin. **The pin mattered a lot while Syncthing was
alive** — Syncthing 1.28 and later moved its DEFAULT configuration directory to
`~/.local/state/syncthing`, so a routine package upgrade on an unpinned install
would have silently switched this machine to the dead second identity and made every
synced folder look brand new. That trap is now irrelevant here, but it is still live
on the other two machines.

## Repository cleanup that followed

- Deleted `machine/systemd/syncthing.user.service`. It was a read only reference copy
  of a unit that no longer exists on any machine we run.
- Deleted `vault/.stignore`. Syncthing ignore rules for a folder Syncthing no longer
  has.
- **KEPT the Syncthing guard in `./skim check`.** That check is the tripwire from the
  2026-04-29 vault deletion and it is still worth having. With the package gone,
  `pgrep -x syncthing` simply always comes back clean, and if anyone ever reinstalls
  and points it back at this repository, the check still shouts.
- **KEPT the Syncthing patterns in `vault/.gitignore`** (`.stfolder/`, `.stversions/`,
  `*.sync-conflict-*`). They cost nothing and they stop a stray conflict file from
  ever being committed if a Syncthing copy of this tree shows up on another machine.

| Unix user | `skim` |

Clone, `machine/bootstrap.sh`, `machine/check.sh`, all eight links healthy on the first

### The gap `bootstrap.sh` leaves on a machine that already had Claude Code

`bootstrap.sh` **keeps** an existing `~/.claude/settings.json` rather than overwriting it,
which is correct and deliberate, and it prints `KEPT ... differs from the template`. On
this machine that line was hiding a real gap: the pre-existing file had **no `hooks` block
and no `statusLine`**. So the workstation would have started every session with no caveman
hook, no statusline, and, more importantly, **no `skim status` at SessionStart** — the one
thing that tells you the machine is behind. `effortLevel` was missing too, and the
`caveman@caveman` plugin was not enabled.

Merged by hand: took `hooks`, `statusLine` and `effortLevel` from
`claude-config/settings.template.json`, kept the machine's own `model`, `theme` and its
four already-installed plugins, added `caveman`, and dropped a stale `autoMode.environment`
block that had been computed when the working directory was `/home/skim` with no git remote
and zero tracked files.

🔑 **`KEPT ... differs from the template` is not a clean result. Diff it.** On any machine
that used Claude Code before this repository existed, assume the hooks are missing.

⚠️ Pasting a large heredoc into this shell mangled the first attempt; the prompt was left
in a quote continuation. `python3 -m json.tool ~/.claude/settings.json` is the check, and
`printf` beats a heredoc for appending a few lines to `~/.ssh/config`.

## Syncthing removed from the office PC

Same evening, 23:17 to 23:50. Machine `Andrea-KAIST-PC-ubuntu`, Unix user `andrea`,
Syncthing device `TP5LGIP-Q6DWZUV-…`.

⚠️ **Its live configuration was `~/.local/state/syncthing`, not `~/.config/syncthing`.**
The 2026-09-16 note above recorded that path as a ThinkPad-only quirk. It is the office
PC's layout as well; `e10ubuntu` was the odd one out because of its pin.

Four folders were configured, all pointing at a single peer, `2LNSMIM…`, which is
`e10ubuntu` — the machine whose Syncthing had been removed hours earlier. So there was no
live peer left in either direction.

| Folder | Path |
|---|---|
| `default` | `/home/andrea/Sync` (only a `.stfolder` marker) |
| `monitoring_project_obsidian_vault` | `~/Monitoring_project/Monitoring_project_obsidian_vault` |
| `neurosurveillance-private` | `~/Monitoring_project/neurosurveillance` |
| `neurosurveillance-system` | `~/Monitoring_project/neurosurveillance-system` |

The last two are the **live `.git` with `versioning: NONE`** hazard recorded on 2026-08-19
as dormant and armed the moment this machine was unpaused. It is now gone for good.

A `config.xml` also carries a `<defaults>` block whose template folder reads
`id="" label="" path="~"`. That is not a real folder pointing at your home directory. Do
not react to it.

Same procedure as `e10ubuntu`: kill `syncthingtray` and its autostart entry,
`apt purge syncthing syncthing-gtk syncthingtray` (28.0 MB), remove the leftovers, and
**move** `~/.local/state/syncthing` to `~/syncthing-config-retired-2026-09-16` rather than
delete it, so a future reinstall is not a brand new device.

### `apt autoremove` is not the same command twice

On `e10ubuntu` the follow-up `sudo apt autoremove` took 13 orphaned Qt libraries. On the
office PC the same command offered **52 packages and 984 MB**, including the whole NVIDIA
570 driver stack (`nvidia-driver-570-open`, `nvidia-dkms-570-open`,
`xserver-xorg-video-nvidia-570`, the `libnvidia-*-570` set) and kernel 6.8.0-117 with its
headers and modules. I had written the step down as safe because it had been safe on the
other machine. It was confirmed before anyone read the list.

It happened to be survivable: the 570 branch was dead weight left over from an upgrade to
580, the running driver is 580.173.02 with `dkms status` showing it built against the
live 6.8.0-136, and grub still found 6.8.0-136 and 6.8.0-124. `nvidia-smi` came back
healthy with Xorg and gnome-shell on the GPU. Nothing needed reinstalling.

🔴 **The real damage was one line further down.** Purging the stranded
`nvidia-driver-570-open` metapackage afterwards printed the **580** stack —
`nvidia-driver-580-open`, `nvidia-dkms-580-open`, `libnvidia-gl-580`, `dkms` — under
"automatically installed and no longer required". The working driver on an RTX 3080 Ti
was one unattended `apt autoremove` from deletion. Pinned:

```
sudo apt-mark manual nvidia-driver-580-open nvidia-dkms-580-open dkms
```

⭐ **`apt autoremove` has no fixed blast radius. Read the list on the machine you are
sitting at, every time.** And after removing any driver metapackage, check what the
replacement's dependencies are now marked as.

### The purge does not kill what is already running

After `apt purge`, `which syncthing` reported nothing while `pgrep -x syncthing` still
returned two PIDs and `systemctl --user list-units 'syncthing*'` still showed
`syncthing.service loaded active running`. systemd keeps a running unit loaded after its
unit file is deleted, and the daemon had been started before the purge. I had also moved
its configuration directory out from under the live process.

`systemctl --user disable --now syncthing.service` then failed with `Unit file
syncthing.service does not exist` — the unit file was already gone with the package.
`pkill -x syncthing` is what actually ended it. Verified afterwards: `pgrep` empty, and
`~/.local/state/syncthing` was **not** recreated, so the moved identity is the only copy.

🔑 **`which` going quiet is not proof the daemon stopped.** Check `pgrep`, and stop the
service before removing the package next time.
