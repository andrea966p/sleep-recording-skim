# 2026-09-23 — The off-site archive turns out to have been empty, and the data gets one name

## TL;DR

The S3 archive was declared working on 2026-09-20. This morning it held **zero
bytes**. Everything else today followed from looking at that.

- **Two defects hid an archive that had never run.** It tried to upload a `.part`
  file, and it could never report `COMPLETE` because it counted subdirectories it
  then skipped — so every successful run raised a false alarm and every failed one
  looked the same. Both fixed. The bucket now holds **133 objects, 1.046 TB**, and
  every file in `~/radix/data` has an off-site copy for the first time.
- **The whole experiment is on the NAS.** W-SD and S-SD were never stripped; they
  are now. All eight canonical analysis windows have a stripped copy and a QC
  bundle.
- **The recording protocol was written down for the first time**, and the act of
  writing it showed that **both sleep-deprivation recoveries stop four hours short
  of it**, missing the hours immediately before sampling. Not recoverable — those
  cohorts were sampled.
- **One name per recording, everywhere.** 110 references across 17 notes, 282
  animal ids across 21 files, and eleven NAS folders were all brought onto the
  registry's naming.
- **283 GB of data deleted** at Andrea's instruction, and 26 GB of redundant text
  exports. Disk went 78% → 64%.

## The archive was empty

`radix-s3-archive.sh` was installed on 09-20 and scheduled for 01:30. Every run
since had deferred, because a recording was live at 01:30 each of those nights.
Nobody noticed, because a backup that has never once run is indistinguishable
from one that works unless somebody opens the bucket.

```
Total Objects: 0
   Total Size: 0
```

Running it by hand exposed two defects immediately.

**It uploaded `.part` files.** The first live run began sending a dead 24-channel
partial left by a crashed strip — 9.1 GB of bytes that were going to change,
into GLACIER_IR, under an IAM user explicitly denied `s3:DeleteObject`. Stopped
before anything landed.

**It could never report `COMPLETE`.** `TOTAL_FILES` came from `ls -1`, which
counts subdirectories; the upload loop then skipped them as non-files. So
`done_files` stopped one short forever and every run took the INCOMPLETE branch,
warning about "0 file(s) failed". Both source directories contain exactly one
such subdirectory, so **both jobs raised a false alarm on every successful run**.

> [!warning] A third defect was invisible until the second fix
> Excluding subdirectories also excluded `_quarantine-2026-08-24-crashed-run/`, a
> real 13 minute recording that therefore had **no off-site copy at all** while
> every file beside it had two. The archiver recurses now, so the next quarantined
> run is archived rather than silently skipped.

## What the protocol page found

Andrea set the standard: every session starts 09:00 KST = ZT0; baseline runs
09:00 → 09:00 (24 h); sleep-deprivation recovery runs 13:00 → 13:00 (24 h),
because 09:00–13:00 is the deprivation itself; ad libitum recovery runs 09:00 →
13:00 (28 h). Both recovery shapes end at sampling.

None of that existed in writing. It lived as prose inside individual run notes,
which is exactly why this had gone unnoticed:

| batch | window | covered | missing |
|---|---|---|---|
| W-SD | recovery | 20.10 / 24 h | **3 h 54 m at the end** |
| S-SD | recovery | 20.08 / 24 h | **3 h 55 m at the end** |

Both SD recoveries stop at 09:05, four hours before the 13:00 sampling. Those are
the hours immediately before the terminal endpoint, and since both cohorts were
sampled, neither run can be repeated.

Two clean windows also turned out not to be the obvious ones. The W-SD baseline's
dated day is split by a nine minute gap, but **08-20 09:00 → 08-21 09:00 is
unbroken inside the restart** and still pre-CSD. The S-SL recovery's dated window
is split too, but **09-21 09:00 → 09-22 13:00 is unbroken inside `uid0921`
alone** and ends at real sampling, which had slipped to 09-22.

Full page: [[CANONICAL-recording-windows-and-protocol]].

## One name per recording

Three separate naming problems, all fixed:

**Recording references.** The same recording appeared as
`allego_0__uid0731-18-06-37`, as `uid0731-18-06-37`, and as `1 uid0731-18-06-37`
where a generated table had split the Allego index into its own column. 110
references in 17 notes were in one of the two broken forms. Only the full form
names a file — `allego_N` is Allego's per-session index and 2026-08-28 alone
produced `allego_3__`, `allego_4__` and `allego_5__`.

The prefixes were not guessed. A uid → index map was built from three independent
sources — the `.xdat.json` headers, `radix-archive.manifest`, and the full-form
references already in the vault — covering 70 recordings with **zero
disagreements**. Eight uids that appeared only in bare form, all long gone from
e10, were recovered from the archive manifest.

**Animal ids.** Both SD cohort manifests used `HLBCSD` for *both* batches, so the
two were indistinguishable by animal id, while the registry separates them as
`HLBWSD01-10` and `HLBSSD11-20`. 282 ids corrected across 21 files.

**NAS folders.** Three shapes had accumulated. All eleven experiment folders now
read `<YYYYMMDD>_<batch><condition>`.

> [!warning] The renames were re-uploads, not `mv`
> `UPLOAD.json` is a verification record — sha256 both ends, read back with the
> CIFS cache dropped. Renaming the folder and editing that file by hand would turn
> a measurement into a claim.

## Three QC bundles were nearly lost

`CACHE_ROOT` was `/tmp/eeg_pipeline_cache`, and `tmpfiles.d` empties `/tmp` on
every boot. Yesterday's 14:58 reboot destroyed the bundles for three recordings
that had **already been stripped**.

That matters more than it sounds. Once a recording is stripped to 16 channels its
wire-free floor is gone from the file forever, and the `.npz` is the only
surviving record of it — which is why `convert/strip_channels` refuses to strip a
recording that has none. They survived only because each had been copied to the
NAS beside its upload, and were recovered from there during the folder renames. A
rename that deleted the old folder first would have lost them for good.

`CACHE_ROOT` is now `~/eeg-qc-cache`. `pipeline/stage1_qc.py` had a *second*,
independent `/tmp` default under its own variable; it derives from the same root
now.

## Deletions

| what | size | why |
|---|---|---|
| `allego_0__uid0829-08-34-39` | 223 GB | an ECG recording, not a sleep batch |
| `allego_0__uid0904-08-55-25` | 58 GB | belonged to something else, 128 ch |
| `per-mouse/**/_raw_1000Hz.txt` | 27.6 GB | lossy CSV of the `.mat` beside it |
| `radix/stripped/test-resume/` | 115 MB | a **truncated** test artefact |

The text exports round to two decimals — `61.815 µV` is written `61.81` — at
three times the size of the `.mat` holding the same signal exactly. The export
script wrote them unconditionally; they are opt-in via `--txt` now, so the space
does not come back.

`test-resume` deserves its own note: its data file was 79,706,112 bytes against
the real 318,824,448, exactly 25%, a deliberately truncated output from testing
resume logic. The archiver's new recursion would have uploaded it tonight — a
truncated file into GLACIER_IR under a path that does not announce itself as
incomplete, beside the complete copy, under an identity that cannot delete it.

## Lessons

- **A backup that has never run looks exactly like one that works.** Nothing but
  opening the bucket would have shown this. The archive now records its object
  count and a 1:1 verification in [[backup-architecture]].
- **An alarm that fires on every successful run trains people to ignore it.** The
  `INCOMPLETE: 0 failed` warning was firing nightly and meant nothing.
- **A cache is not scratch if something refuses to run without it.**
- **`pgrep -f <pattern>` matches the shell that is running the pgrep.** Five
  watcher loops were left spinning today by this and by waiting on a sentinel from
  a job that had been killed. `[ ! -d /proc/<pid> ]` is the version that works.
