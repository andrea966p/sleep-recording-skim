# 2026-07-13 — RustDesk/HDMI-switch crash root-caused; 72h 4-mouse recording audit

## FUTURE FIX — RustDesk + HDMI-switch crashes the desktop session (kills Allego)

> [!warning] Second time this bit us. RustDesk connect / monitor switch → GUI session crash → Allego dies. Fix is forced EDID on the switched HDMI port.

### What happened
While streaming in Allego over RustDesk today, the whole desktop crashed and I got logged out to the GDM login screen. Machine did NOT reboot (uptime still 15 days), it was the Xorg + GNOME **session** that crashed and respawned. Allego died with it.

### Root cause (from journalctl, ~11:34 KST)
- The recording PC drives TWO HDMI outputs:
  - `HDMI-A-1` = 4K-capable, 600 MHz TMDS = the **real monitor coming through the HDMI switch** (the port that appears/disappears when we switch the one shared monitor between the two PCs).
  - `HDMI-A-2` = the **dummy HDMI plug** (stable, keeps RustDesk alive when the monitor is switched away).
- `/proc/cmdline` has NO forced EDID, so the kernel trusts whatever the port reports live.
- At 11:34 the switched port hotplugged (EDID re-probe storm, TMDS clock flipping 330 ↔ 600 MHz over and over), RustDesk's `--server` crashed (`gtk_main_quit: assertion 'main_loops != NULL' failed`), the desktop reconfigured both displays, and under RustDesk on **X11** that reconfigure collapsed the GNOME session. Session daemon logged Allego gone at 11:34:45 (`50051: Connection refused`).
- Same failure family as **Jul 9 19:53**, when Allego "clean quit" 7 seconds after a RustDesk connect + monitor EDID re-probe. So RustDesk + this shared-monitor/dummy setup is the through-line, NOT an Allego bug.

Why the real 72h recording (Jul 10-13) survived: nobody was on RustDesk poking the display during it. The danger is doing remote-desktop work or switching the monitor WHILE acquiring.

### Setup context (why the dummy exists)
One physical monitor, shared between the two PCs (PCs inside the recording room, monitor outside). We switch the monitor between them. The dummy HDMI plug was added so RustDesk doesn't drop the remote connection when the monitor is switched away. Good instinct, but the dummy doesn't stop the mode-set storm the REAL monitor's hotplug creates on the other port.

### Fix — tiered

**Tier 1 — immediate, no config (operational rule):**
- Do NOT switch the physical monitor ONTO the recording PC, or connect/reconnect RustDesk, while Allego is recording. View via RustDesk instead.
- In the RustDesk client, turn OFF "adjust resolution to fit" and set a FIXED resolution.

**Tier 2 — the real future fix (needs a GRUB edit + reboot, do at a downtime gap):**
Force a fixed EDID / mode on the switched port so the kernel ALWAYS presents it as a constant display, regardless of what's physically plugged. Then switching the real monitor in/out changes nothing the desktop sees, no reconfigure, no crash, and we KEEP the switch-to-look ability. Candidate kernel boot param:
```
video=HDMI-A-1:1920x1080@60e
```
(`e` = force the connector enabled always.) Grab the monitor's real EDID first so we pick a mode it likes. TODO: write a step-by-step vault procedure (one sudo command at a time, expected output) before applying.

> [!success] DONE — VALIDATED 2026-07-15
> The fix works, proven by logs. Boot 2026-07-14 19:10 with the param active (`cat /proc/cmdline` shows `video=HDMI-A-1:1920x1080@60e`). On 2026-07-15 09:53 a remote user connected via RustDesk; they reported the screen flickered for **under a second** then stayed fully usable. Logs confirm the session SURVIVED where it used to crash:
> - `gnome-shell` **PID 2730 up continuously since boot (14h49m elapsed)** through the RustDesk connect — the old bug spawned a NEW PID because the session collapsed to GDM. It didn't.
> - **No GDM restart, no segfault, no `gtk_main_quit / main_loops` assert, no `50051: Connection refused`** in the journal (only benign CRON session-close lines).
> - `xrandr`: HDMI-1 locked **1920x1080 primary, stays `connected`**; kernel log shows NO EDID/hotplug re-probe storm. The sub-second flicker = ONE clean modeset, not the storm.
> - Old failure chain (flip → EDID re-probe storm → RustDesk `--server` crash → X11 session collapse → Allego dies) is broken at step 1: `@60e` forces the connector permanently enabled, so a switch flip can't hotplug EDID.
> - Note: the flip test ran with no live recording (the 6.4-min `allego_0__uid0715-09-35-16` QC run had already ended 09:41), so acquisition-during-flip is still unproven, but session survival — the thing that killed Allego — is now confirmed.
>
> ⚠️ 4K is still OFF the table on this thermally-throttled box. If a future kernel/monitor swap ever loses the display, the `6.17.0-29` fallback kernel + `/etc/default/grub.bak.20260714` are the escape hatches.

> [!check]- STAGED 2026-07-14 (awaiting reboot to take effect) — superseded by the DONE callout above
> Applied to `/etc/default/grub` on 2026-07-14 while the next overnight recording was live, so NOT yet active (needs a reboot). Chose **1920x1080@60** not 4K, on purpose: this box is thermally throttled (the wall) and driving 4K costs iGPU watts from the shared 20W RAPL budget + makes RustDesk capture/encode 4× heavier and laggier. 1080p is the right call for a heat-limited, remote-accessed acquisition box.
> - `GRUB_CMDLINE_LINUX_DEFAULT="quiet splash video=HDMI-A-1:1920x1080@60e"` (also cleaned a doubled `quiet splash`).
> - Backup: `/etc/default/grub.bak.20260714`. `update-grub` ran clean, sees kernels 6.17.0-35 (current) + 6.17.0-29 (fallback = console escape hatch if a boot param ever breaks the display). GRUB menu left at timeout 0 (no dual-boot; only Ubuntu — the "menu" was only ever a recovery-kernel picker, not Windows).
> - **Activate:** after stopping the recording at 9am `sudo reboot`.
> - **Validate after reboot:** (1) `cat /proc/cmdline` shows the `video=` param; (2) `DISPLAY=:0 xrandr | grep HDMI-1` = locked 1920x1080, stays `connected`; (3) REAL test = flip the KVM switch off HDMI-A-1 and back while on RustDesk, session + Allego must survive. Then mark this DONE.

**Tier 3 — optional:** if the real monitor is never actually needed on the recording PC, just disable `HDMI-A-1` and run on the dummy only. Simplest, but loses the switch-to-look option.

Plan: Tier 1 now, Tier 2 at the next recording gap.
